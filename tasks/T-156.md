# T-156 — Native output i zamknięte zasoby mają twardy lifecycle

To nie jest optymalizacja „na zapas". Produkcyjne drogi są matematycznie nieograniczone: Check
zbiera cały stdout i stderr do jednego `Vec`, `read_until` pozwala jednej linii bez newline urosnąć
do rozmiaru procesu, dekodery mogą sklonować duże pola do `Value`/`String`/`Line`, a raw evidence
rośnie do rozmiaru wyjścia vendora. Osobno naturalnie zakończony Serve zostaje w mapie, a
`ThreadRegistry.lines` przeżywa zamknięty terminal.

Ten task zamyka wyłącznie output i stan native. Budżet prywatnych needles/obrazów musi być
rozstrzygany przed przyjęciem kolejnej tury, więc należy do wspólnej granicy prywatnego transportu
T-205. Frontendowe feedy, sesje, cache kontekstu i poll procesów należą do T-204.

Ten task wąsko zastępuje byte-exact część T-34 AC-1 wyłącznie ponad jawny limit retencji. Bajty
mieszczące się w limicie pozostają dokładne. Większy strumień jest w całości drenowany, ale
zachowany output ma ograniczone head+tail i jeden jawny marker środka, którego nie zachowano.
Check nadal parsuje cały strumień przyrostowo. Vendorowa ramka większa niż limit ramki jest
odrzucana przed zbudowaniem `serde_json::Value` jako jedna jawnie policzona ramka. Późniejsze
zdarzenia mogą być czytane wyłącznie wtedy, gdy transport nadal ma pewną granicę ramek i
korelację; utrata korelacji zamyka sesję fail-closed zamiast zgadywać odbiorcę odpowiedzi.

`truncated` i `incomplete` są różnymi faktami. `truncated` znaczy: Loadout doszedł do EOF i
świadomie zachował ograniczoną reprezentację. `incomplete` znaczy: odczyt, zapis albo domknięcie
procesu zawiodło i nie wolno twierdzić, że evidence jest pełne. Samo przekroczenie limitu nigdy
nie ustawia `incomplete`; oba fakty mogą być prawdziwe tylko po dwóch osobnych zdarzeniach.
T-207 później składa je do końcowego receipt-u — ten task nie tworzy drugiej księgi evidence.

**Zależy od:** T-153, T-201 i T-210, który ląduje wspólny stos T-202/T-210. Zależność od
T-153 jest operacyjna: semantyka bounded output nie zależy od fan-in, lecz oba taski zmieniają
`src-tauri/src/commands/run.rs` oraz `docs/ARCHITECTURE.md`. Worktree T-156 powstaje dopiero z
exact SHA po integracji T-153; nie wolno kontynuować wcześniejszej gałęzi opartej tylko na T-201.

## Tryb wykonania — FULL HARNESS / large

- Jedyne wejście to `./ship-task.sh T-156 --agent codex --reviewer codex`; pisarz i read-only
  reviewer są osobnymi Codexami na różnych modelach. Nie uruchamiaj domyślnego Claude'a.
- Obowiązują uczciwe czerwone `before`, quick/full, jedna recenzja, najwyżej jedna naprawa i jedno
  `integrate.sh`. Exit 2, invalid oracle albo czerwień po naprawie zatrzymują pracę dla człowieka.
- Jeden neutralny rdzeń `OutputLimits`/bounded capture jest używany przez Check, oba sterowniki,
  App Server i evidence. Wspólna polityka ma dwa jawne tryby: kompletne bounded frames dla NDJSON
  oraz bounded raw bytes dla nieprzezroczystego stderr i Check. Współdzielą limity i prymitywy,
  nie jeden algorytm udający, że każdy strumień jest vendorowym JSON-em. Limity są produkcyjnymi
  wartościami z małymi parametrami konstruktorów w testach, nie alternatywnym `#[cfg(test)]`
  algorytmem ani listą stałych per adapter.
- Nie dodawaj profilera, drugiej pełnej kopii outputu ani artefaktu bez produkcyjnego czytelnika.
  Ciężkie Cargo biegnie pojedynczo na całej maszynie.

## Uczciwe `before`

Wszystkie trzy targety i każdy nowy importowany moduł istnieją przed `./verify.sh before`.
Wykonują rzeczywiste procesy/strumienie oraz setki cykli na małych limitach produkcyjnego typu.
Padają na asercji przekroczonego retained budgetu, braku późnego zdarzenia po ogromnej ramce,
nierozliczonego requestu po utracie korelacji, braku widocznego markera/recovery po przerwaniu
w produkcyjnym readerze albo wpisów native pozostałych po naturalnym końcu/Close. Nie wolno
dowodzić limitu grepowaniem stałej, samą długością fixture, RSS-em całego procesu testowego ani
compile errorem.

## AC-1 Check i strumienie mają bounded working set
check: cargo test --test t156_process_output_is_bounded
expect: (\d+) passed

Wykonywalne atrapy Check, Claude, Codex exec oraz Codex App Server wypisują wielokrotnie więcej
niż skonfigurowane limity. Każda droga obejmuje wiele małych ramek, jedną ogromną linię, której
newline przychodzi dopiero po przekroczeniu limitu, oraz ogromne znane pole tekstowe. Sceny, w
których granica i korelacja pozostają pewne, wysyłają potem poprawne zdarzenie terminalne; osobna
scena App Servera umieszcza response id poza odzyskiwalnym budżetem. Jednorazowe potoki są zawsze
drenowane do EOF bez deadlocka; transport App Servera albo zachowuje pewną korelację, albo jest
kontrolowanie zamykany przez jego lifecycle. Ogromna vendorowa ramka jest jawnie policzona i
odrzucona przed deserializacją. Jeżeli
bounded parser odzyska top-level response id App Servera, dokładnie odpowiadający mu pending
request kończy się typowanym błędem, a poprawna późniejsza ramka może przejść. Jeżeli id nie da się
odzyskać w budżecie, transport/sesja zostaje zatruta i zamknięta, a wszystkie jej pending requesty
rozliczają się dokładnie raz błędem; Loadout nie przypisuje odpowiedzi na chybił-trafił ani nie
obiecuje obsługi następnego requestu. Oversize notification bez response id jest policzona i może
zostać pominięta, jeżeli jej granica ramki pozostaje znana.

Limit obejmuje wszystkie należące do Loadout retained reprezentacje na nazwanych drogach:
bounded bufor ramki albo raw bytes, Check head+tail, stderr complaint, pola dekodera i `Line`,
grupy kuratora, kolejki zdarzeń/outcome/requestów, per-step `said_so_far` używane do handoffu oraz
tymczasową kopię potrzebną do zapisu. Nie jest to obietnica limitu RSS procesu ani wewnętrznych
alokacji `serde`. Oversize frame jest odrzucana przed `serde_json::Value`, a dozwolone duże pola
są przycinane przed zbudowaniem `DecodedEvent`/`AgentEvent`; kontrakt nie wymaga poszerzenia
wspólnego API zdarzeń. Liczba elementów i maksymalny rozmiar jednego elementu mają osobne sufity;
wolny konsument nie zamienia bounded kanału w kolejkę nieograniczonych `Stringów`, a wiele małych
`Said`/tool events nie składa drugiego pełnego outputu w `commands::run`. Target mierzy high-water
mark produkcyjnych bounded typów po setkach ramek, nie tylko długość wartości końcowej.

Check nadal wymaga exit 0 i wzorca dowodu wykrytego przez pełny parser przyrostowy. Dowód położony
w odrzuconym środku nadal przechodzi, a dwa fragmenty po przeciwnych stronach markera nie mogą
sfabrykować dopasowania. `CheckReport.output` i tekst przekazany dalej są ograniczonym head+tail
z angielskim markerem, nigdy drugim pełnym `Stringiem`/`Vec`. Ten sam marker trafia do bounded
`said_so_far` i wynikowego handoffu agenta, więc downstream nie dostaje cicho urwanej prozy.

## AC-2 Ograniczony artifact pozostaje plikową prawdą
check: cargo test --test t156_truncated_evidence_is_file_truth
expect: (\d+) passed

Produkcyjne workflow i rozmowa Lead zapisują stdout/stderr Claude'a, Codex exec oraz istniejące
curated evidence Codex App Servera poniżej i powyżej małych limitów. Poniżej limitu plik jest
byte-exact wobec dozwolonego strumienia tej drogi. Powyżej limitu NDJSON stdout i curated evidence
zachowują wyłącznie kompletne bounded head/tail frames; jedna oversize frame jest zastąpiona w
całości, a separator nie może skleić jej fragmentów w zmyślone zdarzenie vendora. Nieprzezroczysty
stderr i output Check zachowują bounded raw byte head+tail i nie muszą być poprawnym UTF-8 ani
ramkami vendora. Każdy końcowy artifact mieści się w jawnym suficie liczonym razem z markerem i
metadanymi formatu oraz zawiera dokładnie jeden samopiszący marker z `truncated: true`. Żaden temp,
segment ani sidecar nie zawiera ukrytej pełnej kopii, której produkcja nie czyta. Zdrowe EOF daje
`truncated: true, incomplete: false`, a osobny fault odczytu/zapisu zachowuje `incomplete: true`
niezależnie od truncation. Referencja może wskazać tylko plik, który istnieje i mieści się w
limicie.

Osobna scena przerywa produkcyjny writer po przyjęciu części ramek/bajtów, przed zwykłym EOF i
domknięciem, po czym otwiera bibliotekę ponownie przez produkcyjny recovery/reader. Wszystko, co
writer wcześniej potwierdził jako przyjęte, jest widoczne w bounded artefakcie pod produkcyjną
ścieżką, a stan mówi `incomplete: true`; test nie dopisuje ręcznie końca ani nie korzysta z
buforowanej kopii w RAM. Artefakt pozostaje czytelny zgodnie ze swoim trybem, mieści się w limicie
i nie ma pełnego sidecaru. To dowodzi przerwania aplikacji/procesu między zapisami, nie rozszerza
T-210 do obietnicy przeżycia awarii zasilania bez potwierdzonego durable commit.

Target usuwa `loadout.db`, uruchamia produkcyjny `Store::rebuild_from` i otwiera ten sam bieg przez
produkcyjną historię. Oba readery rozpoznają marker jako fakt Loadouta, nie zdarzenie vendora:
odbudowa zachowuje retained zdarzenia przed i po luce oraz dokładnie jeden typowany fakt
truncation, który T-207 później prezentuje człowiekowi. Nie wczytują całego katalogu ani nie
składają na powrót nieograniczonego tekstu. Plik i odbudowany indeks opisują tę samą ograniczoną
prawdę; ten native task nie certyfikuje zdania UI bez produkcyjnego ekranu.

## AC-3 Naturalny koniec i Close naprawdę zwalniają native state
check: cargo test --test t156_closed_native_resources_are_reaped
expect: (\d+) passed

Setki krótkich Serve kończą się pustym `Processes`, zebranym liderem i bez 64 KiB ogona na
wpis. Produkcyjny watcher usuwa naturalnie zakończony wpis bez wymagania dodatkowego list/Stop;
`Processes::list` nie zwraca martwej historii. Ten punkt wąsko zastępuje test T-72, który wymagał
pozostawienia martwego Serve w liście tylko po to, aby frontend zobaczył `alive: false`.

Watcher konsumuje typowany wynik ownership/proof z T-201, nie zgaduje po samym EOF i nie powtarza
TERM → KILL → ESRCH. `Dead` usuwa dokładnie ten wpis, jego ogon i watcher; `Alive`/owned survivor
zostaje z uchwytem i działającym Stopem. Równoległy Stop i naturalny exit rozliczają instancję raz,
a spóźniony watcher adresuje wyłącznie własną niepowtarzalną lokalną tożsamość wpisu. Nie usuwa
innego wpisu nawet po ponownym użyciu PGID przez system; nie wprowadza run generation należącej do
T-155.

Setki terminali watch → conversation → close kończą się zerem wpisów `live` oraz `lines`;
retained Tauri sender nie utrzymuje pompy. Close terminalu bez rozmowy usuwa samo `lines`.
`start -> Err` pozostawia zero actorów, readerów/writerów, senderów i wpisów native. Przerwana
pierwsza tura po `process_started: true` zachowuje ownera i proof lifecycle z T-201; przy `Alive`
actor/owner zostaje adresowalny do ponownego Stop, a sink zamkniętego terminalu nie wraca do mapy.
T-207 jest jedynym właścicielem terminalnego `settled`/`complete`, stosowalności
`process_started`/`death_proof` i prawdy prywatnego receiptu; T-156 nie tworzy ani nie certyfikuje
drugiej semantyki końca. Zamknięcie jednego terminalu nie rusza drugiego; close okna snapshotuje
wszystkie wpisy bez trzymania synchronicznego zamka przez `await`.
