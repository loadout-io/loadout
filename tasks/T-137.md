## Granice implementacji

Publiczną tożsamością pozostaje `NoteAddress { place, id }`, a `place` ma dokładnie dwa
warianty: biblioteka i projekt. Legacy nie jest trzecim miejscem: to `scope: this-project`
fizycznie leżące w bibliotece. Pełne żądanie z okna niesie zamrożone
`{ catalogFolder, place, id }`; okno nigdy nie wysyła ścieżki pliku. Ten sam `id` w obu
miejscach jest poprawny i musi pozostać dwiema pozycjami oraz dwoma kluczami Reacta.

Biblioteka (`~/.loadout/memory`) daje promptowi wyłącznie `everywhere` i `this-agent`.
Projekt (`<zwalidowany-projekt>/.loadout/memory`) daje wyłącznie `this-project` tego projektu.
Biblioteczne legacy jest widoczne, ale nie wchodzi do promptu przed Move. Refleksja zapisuje
nowe `this-project` pod projektem; auto-pamięć `this-agent` i import zostają w bibliotece.

Stempel jest tworzony z dokładnego snapshotu użytego do promptu. W bieżącym lifecycle stempel
powstaje przed skonstruowaniem konkretnego `RunSpec`, ale po zamrożeniu w produkcyjnym planie
`AgentJob.prompt`, który później jest kopiowany byte-identycznie do `RunSpec.prompt`. Dlatego
nowy jednorazowy szew testowy ma uruchomić się dokładnie po zamrożeniu promptu w planie i po
trwałym pierwszym `run.json`, lecz bezpośrednio przed `stamp_what_this_run_carried`.

Szew nie jest polem `RunDeps` i nie rozlewa się na wszystkie wywołania. Dedykowane wejście
workflow w `commands/run.rs` przyjmuje opcjonalny callback używany przez nowy standalone
target; zwykły Run, Ask i trigger zawsze przechodzą `None`. Callback otrzymuje zamrożony
prompt lub równoważny tylko-do-odczytu widok planu, wykonuje się dokładnie raz i nie zastępuje
produkcyjnego stempla. Test osobno dowodzi, że późniejszy prawdziwy `RunSpec.prompt` jest tym
samym zamrożonym tekstem. Nie wolno użyć fabryki `Drivers` jako skrótu: uruchamia się po
snapshotach, ale przed złożeniem finalnego promptu, więc nie mierzy wymaganej granicy.

Move legacy jest protokołem, nie końcowym stanem. Po walidacji i odmowie kolizji czyta źródło,
tworzy temp w katalogu celu, zapisuje i synchronizuje temp, publikuje no-clobber,
synchronizuje katalog celu, usuwa źródło i synchronizuje katalog źródła — dokładnie w tej
kolejności. Zastąp remover-only callback jednym portem `MoveIo` używanym przez jeden rdzeń.
Port ma operacje: `stage_in(target_dir, bytes) -> Pending`, `sync_file(&Pending)`,
`persist_noclobber(Pending, target)`, `sync_dir(dir)` i `remove_file(source)`.

`stage_in` nie dostaje ostatecznej ścieżki celu, więc strukturalnie nie może pisać bezpośrednio
do niej. Shipping `RealMoveIo` i testowy `RecordingMoveIo` są dwiema implementacjami — trait
nie istnieje „na przyszłość”. Rejestrator deleguje rzeczywiste operacje do `RealMoveIo`,
zapisuje literalny ślad i potrafi wstrzyknąć odmowę. Nie wolno użyć callbacka, który tylko
odbiera deklarowany enum `Stage`: implementacja mogłaby wtedy zaraportować „sync” bez
synchronizacji. Polityka kolejności istnieje wyłącznie w jednym rdzeniu, adapter pozostaje
cienki, a stary remover-only szew znika.

Automatyczny zapis sprawdza tombstone po dokładnym prefiksie `<id>__`. Fixture dla kandydata
`similar-slug` musi zawierać tombstone `similar-slug-extra__<czas>.md`: błędne
`starts_with(id)` go stłumi, prawidłowe `starts_with("similar-slug__")` przepuści. Żywa
notatka wygrywa z tombstone, a import ręczny nie jest tłumiony.

Wszystkie mutacje oddają ponownie wyliczony pełny katalog tego samego zamrożonego projektu.
Spóźniona odpowiedź poprzedniego workspace jest ignorowana. Legacy pokazuje wyłącznie
`Move to this project`; po Move zwykłe akcje działają na adresie projektowym.

## Uczciwy `before`

Przed enforced `before` muszą istnieć trzy nowe targety oraz kompilowalne szkielety nowych
typów i funkcji, w tym dedykowanego wejścia workflow z jednorazowym callbackiem
przed-stemplem oraz rdzenia Move z wstrzykiwalnym IO. Rustowe targety mają się skompilować,
uruchomić testy i paść na asercjach zachowania. Browserowy target montuje prawdziwą
aplikację; ma paść na DOM lub taśmie po prawdziwym kliknięciu, nie na imporcie, kolekcji ani
starcie serwera.

Przed `before` nie wolno jeszcze skanować drugiego korzenia, stemplować ze snapshotu,
wykonywać protokołu Move, tłumić dokładnym tombstonem, podpinać adresowanych mutacji ani
chronić przed spóźnionym katalogiem. Brak symbolu, brak targetu, błąd TypeScript, `0 passed`,
`#[ignore]` lub niedopasowany test nie są czerwienią. Dopiero po certyfikacji wolno zastosować
trzy wskazane commity implementacyjne.

## AC-1 Pełny adres, snapshot promptu i exact tombstone są mierzone zachowaniem

check: cargo test --test t137_two_roots_snapshot_and_tombstones
expect: (\d+) passed

Nowy standalone target używa dwóch prawdziwych katalogów projektów i biblioteki. Katalog
porównuje jako dokładny multizbiór `(place, id)`, wraz z licznością, niezależnie od kolejności
zwróconego `Vec`. Ten sam `id` w obu korzeniach daje dwa różne adresy.

Test uruchamia prawdziwy workflow przez `run_workflow_inner` i przechwytuje produkcyjny
`RunSpec.prompt`. Agent A/B dostaje tylko właściwe biblioteczne i projektowe zakresy. Projekt
B zaczyna od surowych bajtów wspólnych notatek sprzed A, osobnych snapshotów biblioteki,
projektu B i całego projektu A; własne stemple B zmieniają tylko niesione pliki, a refleksje
lądują tylko we właściwym projekcie.

Osobna scena zapisuje niesioną notatkę projektową jako dokładne surowe bajty ORIGINAL z
markerem `SEEN-BEFORE-EDIT`, nieznanym kluczem front matter i własnym body. Jednorazowy
callback przed-stemplem najpierw asertuje, że zamrożony prompt planu zawiera ORIGINAL i nie
zawiera EDITED, następnie zwykłym testowym `fs::write` podmienia ten sam fizyczny plik na
drugą poprawną notatkę z markerem `EDITED-AFTER-PROMPT` i odczytuje ją z dysku, dowodząc
wykonania podmiany. Callback uruchamia się dokładnie raz.

Dubler sterownika przechwytuje późniejszy prawdziwy `RunSpec.prompt`: nadal zawiera ORIGINAL,
nigdy EDITED, i jest równy promptowi widzianemu przez callback. Po zakończeniu workflow plik
ma niepusty `last_used_at`; po znormalizowaniu wyłącznie tej jednej linii do `null` jest
bajtowo równy ORIGINAL, zachowuje nieznany klucz i body oraz nie zawiera żadnego markera
EDITED. Implementacja ponownie czytająca ścieżkę przy stemplu zachowałaby EDITED i musi
przegrać. Test nie śpi, nie ściga watchera i nie używa produkcyjnego helpera jako wyroczni.
Wykluczona notatka zmieniona w tym samym oknie pozostaje nietknięta przez stempel.

Adresowane Use/Stop/Discard, legacy odmowy, pełny katalog oraz prawdziwy filesystemowy Move
zachowują zachowania T-136. Tombstone `similar-slug-extra__2026-08-26T10-30-00Z.md` nie tłumi
kandydata `similar-slug`; dokładne tombstone'y projektu i biblioteki tłumią, żywa notatka
wygrywa, a `record_imported` przechodzi. Test nie czyta źródła produkcyjnego i nie używa
helpera produkcyjnego jako własnej wyroczni.

Historyczne fixture wymienione w `OWNS` zachowują oryginalne asercje, lecz projektowe
`this-project` zasiewają i skanują pod `<projekt>/.loadout/memory`. T-126 nadal dowodzi
prywatnej refleksji i późnego Stopu na korzeniu projektu. Pełna bramka ma przejść bez
osłabiania starych asercji.

## AC-2 Protokół Move jest obserwowalny przed pierwszą operacją niszczącą

check: cargo test --test t137_move_durability_protocol
expect: (\d+) passed

Target woła ten sam rdzeń protokołu, którego używa produkcyjny `move_note_to_project`.
`RecordingMoveIo` deleguje prawdziwe operacje do `RealMoveIo` i zapisuje wyłącznie to, co sam
wykonał. Fixture sadzi źródło z literalnych `FIXTURE_BYTES`; oczekiwanie nie pochodzi z
odczytu źródła ani helpera produkcyjnego. Sukces ma dokładny ślad:

1. `StageIn(target_dir, FIXTURE_BYTES)`;
2. `SyncFile(temp)`;
3. `PersistNoClobber(the_same_temp, target)`;
4. `SyncDir(target_dir)`;
5. `RemoveFile(source)`;
6. `SyncDir(source_dir)`.

Rzeczywista ścieżka tempa ma rodzica `target_dir`, różni się od `target`, a ten sam
identyfikator tempa przechodzi przez Stage, Sync i Publish. Przed `RemoveFile` istnieje pełny,
zsynchronizowany i opublikowany cel. Po sukcesie istnieje wyłącznie cel z `FIXTURE_BYTES`,
a źródła i tempa nie ma.

Kolizja widoczna już w prechecku odmawia przed `StageIn` i nie zmienia źródła ani celu.
Osobny wariant najpierw raportuje brak celu, a następnie tworzy konkurencyjny cel dopiero
wewnątrz `PersistNoClobber`: Move odmawia, nie nadpisuje konkurencyjnych bajtów, zachowuje
źródło i nie wykonuje późniejszego `SyncDir` ani `RemoveFile`.

Tabela wstrzykniętych odmów dowodzi granic destrukcji: odmowa `SyncFile` zostawia źródło bez
finalnego celu; odmowa `SyncDir(target_dir)` zostawia pełne źródło i pełny cel bez unlinku;
odmowa `RemoveFile` zostawia dwie pełne kopie i nie synchronizuje katalogu źródła; odmowa
`SyncDir(source_dir)` zwraca błąd, ale pełny cel pozostaje, a źródło jest już usunięte. Żaden
scenariusz nie kończy z zerem pełnych kopii. Oracle nie używa `include_str!`, nie grepuje
`persist_noclobber`, `sync_all`, `rename` ani komentarzy i nie uznaje samych nazw metod za
dowód.

## AC-3 Człowiek naprawdę wykonuje Move, Use, Stop i Discard na pełnym adresie

check: npx --no-install vitest run e2e/tests/t137-memory-addresses-real-actions.spec.ts
expect: (\d+) passed

Spec używa wyłącznie `e2e/harness.ts`, montuje prawdziwą aplikację i klika sekcję Memory.
Opóźnia katalog A, przełącza na B, rozlicza B, a potem starą odpowiedź A; DOM pozostaje B i
każde późniejsze wywołanie niesie zamrożony folder B.

Legacy stoi w `Earlier project notes`, ma prawdziwe angielskie zdanie i wyłącznie
`Move to this project`. Kliknięcie wysyła dokładnie
`{ catalogFolder: B, place: library, id: legacy }`; pełna odpowiedź przenosi wiersz do
projektu. Następnie spec klika Use, Stop i Discard na projektowym wierszu z `id`, który nadal
istnieje w bibliotece. Każde żądanie niesie dokładnie
`{ catalogFolder: B, place: project, id }`.

Po każdej odpowiedzi test porównuje dokładny multizbiór widocznych adresów oraz nowy unikalny
marker nietkniętego bibliotecznego wiersza. Po Discard znika wyłącznie projektowy duplikat;
biblioteczny duplikat i przeniesione legacy pozostają. `data-note-address` służy tylko do
lokalizacji wiersza — dowodem poprawnego React key jest niezależne zachowanie obu wierszy
przez cztery pełne wymiany katalogu, nie sam atrybut.

Na końcu przefiltrowana taśma ma dokładnie kolejność: `list_notes(A)`, `list_notes(B)`,
`move_note_to_project`, `put_note_to_use`, `stop_using_note`, `discard_note`, bez dodatkowej
mutacji. Spec nie podaje testowych propsów, nie montuje samego `NoteRow`, nie woła settera
Zustand ani helpera akcji bez kliknięcia i nie używa `waitForTimeout` jako jedynego dowodu.
