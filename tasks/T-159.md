# T-159 — Prywatny stan Claude'a zachowuje systemowe logowanie

Claude Code 2.1.247 rozdziela nie tylko stan, ale także przestrzeń bezpiecznych poświadczeń
na podstawie `CLAUDE_CONFIG_DIR`. T-109 ustawiło osobny katalog na każdy krok, żeby równoległe
procesy nie uszkadzały wspólnego `.claude.json`; skutkiem ubocznym jest osobny, pusty wpis
Keychain dla każdego kroku i natychmiastowe `Not logged in · Please run /login`.

Vendor ma osobny szew `CLAUDE_SECURESTORAGE_CONFIG_DIR`. Pusta wartość zachowuje domyślną,
systemową przestrzeń Keychain, podczas gdy `CLAUDE_CONFIG_DIR` nadal izoluje zapisywalny stan.
Naprawa nie kopiuje, nie czyta i nie zapisuje tokenów, `.credentials.json`, `~/.claude/` ani
`~/.claude.json`; nie osłabia też równoległości z T-109.

**Tryb właścicielski:** mały hotfix Codex w osobnym worktree, bez `ship-task.sh`, review i rundy
repair. Obowiązują uczciwe `before`, celowany test i `./verify.sh quick`; po integracji ręczna
sonda prawdziwego `claude auth status` z oboma zmiennymi środowiskowymi.

## Uczciwe `before`

Target istnieje i uruchamia produkcyjny `ClaudeDriver` z wykonywalną atrapą. Przed poprawką
proces startuje, ale asercja pada, bo nie dostaje jawnej wspólnej przestrzeni secure storage.
Brak testu, błąd kompilacji albo zero wykonanych testów nie są czerwienią.

## AC-1 Izolowany krok korzysta z systemowego logowania Claude'a
check: cargo test --test t159_claude_auth_with_private_state
expect: (\d+) passed

Dwa równoległe kroki przechodzą przez produkcyjny `ClaudeDriver`. Atrapy dowodzą, że każdy ma
inny, bezwzględny `CLAUDE_CONFIG_DIR`, a oba mają dokładnie
`CLAUDE_SECURESTORAGE_CONFIG_DIR=""`. Hostile wartość tej zmiennej dostarczona przez konfigurację
agenta jest zastępowana przez politykę sterownika. Żaden plik poświadczeń nie powstaje w katalogu
biegu, globalny sentinel w fałszywym `HOME` pozostaje bajt w bajt bez zmian, a oba procesy
kończą się sukcesem z nakładaniem w czasie.
