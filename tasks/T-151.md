# T-151 — Nowsze bajty wygrywają, a Run używa widocznej rewizji

To zadanie zamyka jedną klasę błędów: wynik spóźnionej operacji nie może cofnąć nowszego
stanu. Dotyczy to stempla pamięci, zapisu plików będących prawdą, listowania uszkodzonych
workflowów i agentów oraz kliknięcia Run w czasie autosave.

T-139 świadomie certyfikuje dziś odwrotną semantykę: po edycji wykonanej po zamrożeniu promptu
stempel przywraca bajty snapshotu. Ten fragment kontraktu zostaje tutaj jawnie zastąpiony.
Prompt i receipt nadal opisują zamrożony snapshot, ale metadane nie mają prawa cofnąć żywego
pliku. Pozostałe zachowania T-139 zostają bez zmian.

**Zależy od:** T-150 i T-152. T-150 współdzieli `src-tauri/src/lib.rs`, a T-152 kończy zmianę
`AppState`/IPC przed wprowadzeniem typowanego wyniku listowania.

**Read first:** `AGENTS.md` §2a oraz niezmienniki 2, 4, 19, 21, 24 i 25 ·
`tasks/T-139.md` i jego aktualny target snapshotu · `src-tauri/src/memory/notes.rs`
(`mark_used_from_snapshot`, `persist`) · `src-tauri/src/workflow/file.rs` ·
`src-tauri/src/library/agents.rs` · `src-tauri/src/memory/handoff.rs` ·
`src-tauri/src/commands/{agents,workflows}.rs` · `src-tauri/src/ipc.rs` ·
`src/sections/{agents,workflows}/` · `src/state/{agents,workflows}.ts`.

## Tryb wykonania

- **Agent:** Codex w osobnym worktree, bez `ship-task.sh`.
- **Druga opinia:** osobny Codex na innym modelu, tylko do odczytu. To zatwierdzony przez
  właściciela wariant D3 z powodu małego pozostałego budżetu Claude'a.
- Wywołania: `./review.sh --agent codex --reviewer codex`, a jeśli są uwagi, dokładnie raz
  `./repair.sh --agent codex --reviewer codex`. Nie uruchamiaj domyślnego agenta Claude.
- Obowiązują czerwone `before`, quick/full, jedna recenzja, najwyżej jedna naprawa i pojedyncze
  `integrate.sh`. Nie zmieniaj `harness/`, `checks/` ani `verify.sh`.

## Uczciwe `before`

Wszystkie pięć targetów i każdy nowy importowany moduł istnieją przed `./verify.sh before`.
Rustowe szkielety się kompilują, frontendowe dają się zebrać, a testy padają na asercji
starych bajtów, złej kolejności lub ukrytej pozycji. Brak modułu, błąd kompilacji, zero testów
i sztuczny sentinel nie są czerwienią.

## AC-1 Stempel nie cofa edycji, Move ani Discard
check: cargo test --test t151_note_stamp_preserves_newer_truth
expect: (\d+) passed

Target uruchamia prawdziwą granicę snapshot → stempel. Po zamrożeniu promptu wykonuje osobno:

- edycję body, `modified` i nieznanego klucza front matter — wszystkie nowsze bajty przeżywają,
  a w aktualnym pliku zmienia się wyłącznie `last_used_at`;
- Move — stara ścieżka nie wraca, a cel nie jest nadpisany snapshotem;
- Discard — notatka pozostaje odrzucona i nie jest wskrzeszana;
- zmianę tożsamości/fingerprinta pod tym samym adresem — stempel odmawia zamiast dotknąć
  innej notatki.

Zamrożony `RunSpec.prompt` i receipt nadal zawierają wcześniejszą wersję, czyli bieg nie zmienia
kontekstu w połowie. Aktualny target T-139 zostaje skorygowany wyłącznie w asercjach, które
żądały utraty `T139-EDITED-AFTER-PROMPT`; pełna reszta jego scenariusza ma pozostać zielona.

## AC-2 Workflow, agent i handoff publikują cały plik albo nic
check: cargo test --test t151_truth_files_publish_atomically
expect: (\d+) passed

Jeden wspólny rdzeń rozróżnia dwie operacje. `atomic replace` wykonuje temp w katalogu celu →
pełny zapis → `sync_all` pliku → atomową podmianę → synchronizację katalogu. `atomic
create-if-absent` publikuje bez nadpisania istniejącego celu; dwa równoległe identyczne claimy
dają jednego zwycięzcę i jeden jawny konflikt. Używają ich normalne zapisy workflowów, agentów
i handoffów. Fault-injection przed i w commit point zostawia dokładnie stare bajty albo pełne
nowe bajty, nigdy pusty/pół pliku, rezerwację bez treści ani temp. Sukces daje plik, który
produkcyjny loader czyta ponownie. Bezpośrednie `fs::write` celu ma oblać test.

Handoff jest transakcją attachment + pointer + zmiana statusu poprzednika. Test przerywa proces
po każdym z tych etapów i otwiera bibliotekę ponownie: widoczny jest dokładnie jeden aktywny,
czytelny handoff, bez broken pointera i bez dwóch aktywnych wersji. Loader wykonuje jawnie
testowaną recovery/cleanup przed odczytem; nie powstaje martwy journal. Prywatne pliki zachowują
`0600`, nie przechodzą przez symlink i nie są publikowane poza kontrolowanym katalogiem.

Migracje SQLite i atomowy importer nie są zakresem tego zadania.

## AC-3 Jeden zepsuty plik nie ukrywa zdrowej biblioteki
check: cargo test --test t151_bad_definition_is_isolated
expect: (\d+) passed

Biblioteka zawiera dwa zdrowe workflowy, dwóch zdrowych agentów, uszkodzony JSON workflowu i
uszkodzony Markdown agenta. Produkcyjne listowanie zwraca przez prawdziwe IPC typowaną tablicę
`Healthy | DefinitionProblem`: wszystkie zdrowe pozycje oraz osobny problem z bezpieczną ścieżką
każdego wadliwego pliku. Zdrowy wariant zachowuje dotychczasowy wire shape, więc istniejące drogi
Run/Ask i browser harness nadal dostają zwykłe zdrowe elementy; wspólny adapter rozdziela union,
nie ekrany. Problem nie zgaduje pól definicji, nie zamienia całej listy agentów na pustą i nie
przerywa listy. Ponowny poprawny zapis wadliwego pliku usuwa problem bez restartu.

## AC-4 Człowiek widzi wadliwy plik, a zdrowe pozycje nadal działają
check: npx --no-install vitest run src/sections/t151-bad-library-files-are-actionable.test.tsx
expect: (\d+) passed

Target renderuje prawdziwy ekran Workflows i Agents z wynikiem IPC z AC-3. Nazwa każdego
wadliwego pliku i angielskie zdanie są widoczne; wpisu nie da się otworzyć, zduplikować ani
uruchomić jako zmyślonej definicji. Path-aware Delete usuwa dokładnie wskazany wadliwy plik po
potwierdzeniu i odświeża listę. Zdrowy workflow nadal daje się otworzyć/uruchomić, a zdrowy agent
edytować. Test nie montuje samego helpera ani nie podaje problemu propsem, którego produkcyjny
caller nie ma.

## AC-5 Natychmiastowy Run czeka na dokładnie tę edycję
check: npx --no-install vitest run e2e/tests/t151-run-uses-visible-workflow-revision.spec.ts
expect: (\d+) passed

Spec korzysta z istniejącego `e2e/harness.ts`, zmienia widoczne pole workflowu i natychmiast
klika Run, przed upływem 400 ms. Taśma musi pokazać, że zapis dokładnie tej rewizji zakończył
się przed `run_workflow`. Starszy zapis in-flight nie może później nadpisać nowszego.
Błąd zapisu zostawia człowieka w edytorze, pokazuje angielskie zdanie i nie uruchamia biegu.
Test nie woła `saveNow`, store ani handlera Run bezpośrednio.
