# T-202 — Plik będący prawdą jest publikowany w całości albo wcale

Workflowy i agenci zapisują dziś bezpośrednio do celu przez `fs::write`. Handoff otwiera nazwę
końcową przed pełnym zapisem, a duży attachment jest zapisywany osobno przed pointerem bez
wspólnej granicy durability. Awaria procesu lub dysku może więc zostawić pusty/pół pliku,
widoczny pointer do nieistniejących bajtów albo publikację przez symlink poza kontrolowany
katalog.

Repo ma już prywatny atomowy publisher w supervisorze, używany przez produkcyjny zapis JSON
evidence. Ten task wyciąga z niego **jeden** trwały rdzeń i używa go także dla workflowów,
agentów, zwykłych handoffów oraz attachments. Rdzeń ma dwie jawne operacje: replace istniejącej
prawdy i create-if-absent dla niepowtarzalnego claimu. Nie powstaje drugi adapter per biblioteka.

**Zależy od:** brak.

**Read first:** `AGENTS.md` niezmienniki 3, 4, 9, 19, 21, 23 i 24 ·
`src-tauri/src/engine/supervisor.rs` (`PrivateFilePublisher`) ·
`src-tauri/src/evidence.rs` (`atomic_json`, istniejący produkcyjny caller) ·
`src-tauri/src/workflow/file.rs` · `src-tauri/src/library/agents.rs` ·
`src-tauri/src/memory/handoff.rs` (`persist`, attachment, `supersede`).

## Tryb wykonania — FULL HARNESS / large

- Jedyne wejście to `./ship-task.sh T-202 --agent codex --reviewer codex`. Pisarz i read-only
  reviewer są osobnymi Codexami na różnych modelach; nie uruchamiaj domyślnego Claude'a.
- Harness prowadzi uczciwe czerwone `before`, quick/full, jedną recenzję i najwyżej jedną rundę
  `repair.sh --agent codex --reviewer codex`. Exit 2, invalid oracle albo czerwień po naprawie
  zatrzymują pracę dla człowieka.
- Jedyne lądowanie to pojedyncze `integrate.sh` dla gałęzi zwróconej przez Harness. Nie zmieniaj
  `harness/`, `checks/` ani `verify.sh`.
- Fault injection korzysta z małego produkcyjnego interfejsu publikacji i katalogów tymczasowych,
  nie z `#[cfg(test)]`-owego alternatywnego algorytmu. Ciężkie Cargo biegnie pojedynczo.

## Kontrakt wspólnego publishera

`atomic_replace` tworzy losowy plik tymczasowy przez exclusive create w **tym samym katalogu**
co cel, ustawia docelowy tryb, zapisuje pełne bajty, wykonuje `sync_all` pliku, atomowo podmienia
nazwę i synchronizuje katalog. `atomic_create_if_absent` przygotowuje i synchronizuje taki sam
pełny temp, a następnie publikuje go bez możliwości nadpisania istniejącego celu; dwa równoległe
claimy dają jednego zwycięzcę i jeden typowany konflikt. Publikacja nie tworzy pustej rezerwacji,
która może przeżyć bez treści.

Obie operacje:

- walidują bezpieczną nazwę oraz kontrolowany root i nie przechodzą przez symlink w żadnym
  komponencie ani w celu; sprawdzenie i publikacja nie są rozdzielone wyścigiem
  `canonicalize → późniejsze otwarcie ścieżki`;
- nigdy nie tworzą tempu poza katalogiem celu ani na innym filesystemie;
- propagują błąd zapisu, syncu, commit pointu i syncu katalogu; sukces oznacza durable nazwę,
  nie tylko opróżniony userspace buffer;
- po obsłużonym błędzie usuwają swój temp. Po realnym crashu produkcyjny loader przed listowaniem
  rozpoznaje wyłącznie własny wzorzec tempów, zachowuje prawidłowy cel i idempotentnie sprząta
  resztę; nigdy nie usuwa obcego pliku;
- stosują jedną jawną politykę uprawnień. Handoff, attachment i prywatne evidence mają `0600`
  jeszcze przed publikacją. Workflow i agent zachowują ustalony tryb definicji przy
  replace, a nowy plik dostaje jeden udokumentowany owner-writable default.

Kod zależny od platformy nie wychodzi poza `engine/supervisor.rs`. Jeśli implementacja wspólnego
publishera nie potrzebuje platformowego `cfg`, cały rdzeń mieszka w `durable_file.rs`; adapter
supervisora tylko wybiera kontrolowany root, tryb i operację.

## Uczciwe `before`

Oba dokładne targety i moduł `durable_file` istnieją oraz kompilują się przed
`./verify.sh before`. Targety wywołują produkcyjne save/load workflowu i agenta oraz produkcyjne
`handoff::persist`; fault pointy są osiągane po prawdziwym zapisie i syncu, a scena concurrency
używa dwóch wątków. Padają na asercji pustego/pół pliku, nadpisanego claimu, broken pointera,
złych praw albo pozostawionego tempu. Brak modułu, compile error, zero testów, grep
`fs::write` i test samej stałej nie są czerwienią.

## AC-1 Workflow i agent używają jednego trwałego replace
check: cargo test --test t202_atomic_definition_publication
expect: (\d+) passed

Target zapisuje i produkcyjnie ładuje istniejący oraz nowy workflow i agent. Dla każdego fault
injection odmawia po utworzeniu tempu, po częściowym/pełnym zapisie, po syncu pliku, w commit
point oraz przy syncu katalogu. Po reopen loader widzi dokładnie stare bajty albo cały nowy plik,
nigdy pustą lub mieszaną definicję. Każdy wariant sukcesu daje definicję, którą obecny loader
parsuje bez specjalnej ścieżki testowej.

Osobne sceny podstawiają symlink jako komponent katalogu i jako nazwę celu, próbują `..` oraz
absolutną ścieżkę poza rootem. Wszystkie odmawiają przed publikacją, nie zmieniają pliku poza
rootem i nie pozostawiają tempu. Tryb istniejącego pliku definicji przeżywa replace, a nowy plik
ma udokumentowany owner-writable default.

Target uruchamia również oba prymitywy bezpośrednio przez produkcyjny typ: dwa równoległe
`atomic_create_if_absent` tej samej nazwy publikują pełne bajty dokładnie jednego claimu, drugi
dostaje konflikt, a późniejszy replace daje pełną nową wersję. Awaria po opublikowaniu nazwy,
lecz przed cleanupem tempu, jest odtwarzana przez reopen: cel pozostaje czytelny, a własny temp
znika. Istniejący produkcyjny caller evidence używa tego samego rdzenia i zachowuje `0600`.

Jedna współdzielona instancja produkcyjnego publishera z kontrolowanym fault pointem przechodzi
kolejno przez save workflowu, save agenta, produkcyjny zapis JSON evidence i handoff z
attachmentem. Licznik dowodzi, że każdy caller wszedł do tego samego rdzenia; dawny
`PrivateFilePublisher` nie pozostaje drugim właścicielem polityki, a kompatybilny re-export z
supervisora wyłącznie chroni istniejącego callera. Bezpośredni zapis nazwy końcowej w którymkolwiek
z tych callerów oblewa scenę faultu.

## AC-2 Attachment jest trwały zanim handoff stanie się widoczny
check: cargo test --test t202_handoff_publication_is_durable
expect: (\d+) passed

Mały zwykły handoff publikuje kompletny Markdown przez `atomic_create_if_absent`. Duży handoff
najpierw publikuje i synchronizuje pełny attachment `0600`, a dopiero potem publikuje końcowy
Markdown pointer. Loader nigdy nie obserwuje pointera do brakującego albo częściowego attachmentu.
Dwa równoległe claimy tej samej nazwy dają dokładnie jeden czytelny handoff i jeden jawny konflikt;
zwycięzca nie jest wybierany przez nadpisanie.

Target przerywa po pełnym zapisie attachmentu, po jego publikacji, przed pointerem i w commit
point pointera, po czym otwiera bibliotekę produkcyjnym loaderem. Widoczny jest albo poprzedni
stan, albo jeden kompletny handoff z kompletnym attachmentem. Attachment osierocony przed
pointerem jest niewidoczny jako handoff i zostaje idempotentnie usunięty przez recovery; nie
powstaje broken pointer, drugi aktywny wpis ani martwy journal. Prywatne pliki mają `0600`,
nie przechodzą przez symlink i nie wychodzą poza run root.

`handoff::supersede` nie ma produkcyjnego callera. Ten task nie buduje dla niego transakcji
attachment + pointer + zmiana statusu poprzednika, nie dodaje journalu i nie certyfikuje
dwóch aktywnych wersji. Jeśli supersede stanie się funkcją produktu, dostanie osobny kontrakt
z realnym czytelnikiem; niezmiennik 21 zabrania artefaktu recovery „na przyszłość".
