# T-204 — Każdy terminal prezentuje właściwy bieg i zwalnia zamknięty stan

T-155 kończy backendową tożsamość wielu biegów, usuwa globalne `going`, prowadzi adres przez
wszystkie produkcyjne callery i zostawia aktualne okno działające. Nadal istnieje jednak routing
widoku według tego, co akurat jest na wierzchu, sesja/cache kluczowane zbyt szeroko oraz
spóźnione odpowiedzi, które mogą nadpisać inną kartę. T-156 zamyka zasoby native, lecz świadomie
nie dotyka Reacta ani modułowych rejestrów. Ten task konsumuje gotowy `RunAddress` z T-155 i
nadaje frontendowej prezentacji pełny klucz: terminal, canonical workspace i run UUID, a stary
async wynik nie może przejąć kontekstu innej karty ani innego runu.

**Zależy od:** T-154, T-155 i T-156.

**Read first:** `AGENTS.md` niezmienniki 5, 6, 7, 13, 16, 19, 23, 24 i 29 ·
`tasks/T-71.md` · `tasks/T-155.md` (gotowy `RunAddress`, lifecycle i terminal-close event) ·
`src/ipc/run.ts` · `src/state/{run,run-tabs}.ts` · `src/sections/run/io.ts` ·

## Tryb wykonania — DIRECT / medium

1. Codex tworzy osobny worktree przez `./worktree.sh T-204`; nie używa `ship-task.sh`,
   `review.sh` ani `repair.sh`.
2. Najpierw dodaje trzy kompletne targety oraz kompilowalny szkielet wspólnej eviction edge.
   Uruchamia każdy `check:` osobno. Czerwień ma być asercją routingu do karty na wierzchu,
   folderowego cache albo retained state po produkcyjnym Close. Adresowanie i odmowa Stopu są
   już oraclami T-155, więc nie mogą udawać czerwieni tego taska. Collection error, brak modułu,
   timeout, zero testów i test store'a bez prawdziwego callera nie są dowodem.
3. Implementuje wyłącznie `OWNS`, uruchamia trzy targety i `./verify.sh quick`; osobny Codex
   robi lekki read-only review diffu bez `review.sh`. Jedynym lądowaniem jest pojedyncze
   `./integrate.sh <gałąź>`, które wykonuje pełną bramkę.
4. `e2e/harness.ts` może dostać wyłącznie małą krawędź dostarczającą gotową typowaną paczkę
   T-155 do Tauri `Channel`; nie wybija UUID, nie buduje adresu i nie implementuje registry,
   limitera, retry ani routingu Rusta.

## Kontrakt frontendowej tożsamości

T-204 nie wybija UUID, nie odczytuje bieżącego folderu, nie kanonizuje ścieżki i nie buduje
argumentów Stop/Continue/Say/Close. T-155 dostarcza gotowy `RunAddress { identity, owner }` oraz
`RunPacket`; ten task tylko kluczuje i routuje prezentację. Brak adresu pozostaje widoczną odmową
T-155, nie okazją do odgadnięcia go z aktywnej karty. `Trigger` nie jest zamieniany na terminal
i jego paczka nie trafia do przypadkowo aktywnego feedu.

Stan prezentacji biegu jest per `(terminal, canonical workspace, run UUID)`. Kontekst agenta
nie może przejąć wyniku z innego terminalu ani innego runu tylko dlatego, że folder albo nazwa
kroku są takie same. Zdarzenie innego runu lub terminalu nie trafia do aktywnego feedu. Dwa
terminale wskazujące ten sam workspace mają jeden backendowy bieg, lecz feed i kontrolki dostaje
wyłącznie `Terminal { terminal_id }` będący ownerem.

Wspólna eviction edge obserwuje produkcyjne zamknięcie terminalu z T-155 i ma jeden mechanizm
generation fencing dla wszystkich rejestrów. Idle albo prawdziwie settled Close usuwa stan.
`CleanupNeeded` nie jest zamknięciem: karta, pełny adres i Retry Stop pozostają widoczne aż do
pasującego `Dead`. Samo rozwiązanie future, `finally`, przełączenie karty ani pakiet starego UUID
nie uruchamiają eviction.

## AC-1 Spóźniony context request nie nadpisuje innego terminalu ani innego runu
check: npx --no-install vitest run src/sections/run/session/t204-context-is-keyed-by-run-and-step.test.tsx
expect: (\d+) passed

Target montuje prawdziwy `AgentScreen` oraz produkcyjny IO/cache i kontroluje kolejność Promise.
Odczyt A startuje, potem B; B kończy pierwszy, A ostatni, a ekran pozostaje przy B bez handoffów,
notatek ani kontekstu A. Następna scena uruchamia nowy run w tym samym workspace: wynik starego
runu nie może nadpisać nowego tylko dlatego, że folder i etykieta kroku się zgadzają. Błąd
bieżącego żądania daje pusty bieżący stan i angielskie zdanie, nie cache poprzednika.

Target dochodzi przez prawdziwy mount i przełączenie zaznaczonego kroku. Nie woła cache helpera
bezpośrednio i nie podaje komponentowi klucza, którego produkcyjny caller nie ma.

## AC-2 Dwa workspace'y mają niezależne feedy i live UI w prawdziwym widoku
check: npx --no-install vitest run e2e/tests/t204-two-workspaces-run-independently.spec.ts
expect: (\d+) passed

Spec otwiera terminal A, startuje bieg przez produkcyjną drogę T-155, przełącza na workspace B
i startuje drugi. Obie karty mają własną live dot, feed, liczbę agentów oraz różne gotowe
biegi; powrót do A pokazuje wszystkie jego linie. Paczka A, która przychodzi, gdy B jest na
wierzchu, trafia wyłącznie do A. Pełna globalna pula pokazuje na C angielskie Waiting, a po
zwolnieniu slotu ten sam zarezerwowany run startuje automatycznie bez busy-loopu i bez pomylenia
feedu lub live dot.

Drugi terminal wskazujący workspace A nie duplikuje feedu ani kontrolek. Zmiana aktywnej karty
albo workspace'u nie przepina istniejących linii do przypadkowo widocznego widoku.

Brak globalnego `going` jest zależnością odziedziczoną po T-155, nie implementacją tego taska.
Pending/Waiting jest per run, prezentacja per terminal, a wspólny limit pozostaje wyłącznie
backendowym faktem T-155. Uczciwe `before` pada po starcie obu backendowych biegów na złym
routingu/live dot albo pomieszanym feedzie, nie na odmowie singletonu już usuniętej przez T-155.

## AC-3 Rozliczony Close ewakuuje frontend i stary async wynik go nie wskrzesza
check: npx --no-install vitest run src/sections/run/t204-closed-ui-state-is-evicted.test.ts
expect: (\d+) passed

Setki idle albo prawdziwie settled terminali otwartych i zamkniętych produkcyjnym handlerem
wracają do baseline'u rejestrów feedów, kontekstu kroków i polli procesów. Przełączenie aktywnej,
nadal otwartej karty zachowuje jej pełną historię; tylko rozliczony Close jest granicą retencji.

Każdy rejestr korzysta z jednej wspólnej eviction edge podpiętej do prawdziwego Close T-155.
Jeśli backend odpowiada `CleanupNeeded`, nic nie jest ewakuowane: karta, adres i Retry Stop
pozostają, a późne `finally` nie może ich zdjąć. Dopiero pasujący terminalny `Dead`/settled
uruchamia eviction. In-flight context request i poll procesów niosą generation/identity;
odpowiedź starej generacji po Close jest odrzucana i nie odtwarza mapy. Poll procesów jest
single-flight, a spóźniona starsza odpowiedź nie może cofnąć nowszej ani wskrzesić martwego
wpisu.

Ten AC zastępuje wyłącznie część T-71 wymagającą historii po zamknięciu terminalu. Historia
otwartych kart, przełączanie bez utraty i izolacja per terminal pozostają.
