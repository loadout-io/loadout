# T-155 — Backend adresuje żywe biegi kanonicznym workspace i UUID

T-24 i ARCHITECTURE obiecują aktywne biegi w kilku workspace'ach, ale produkcyjny `AppState`
ma jeden globalny `live: RunControl`. Drugi poprawny Start albo odmawia dlatego, że pracuje inny
folder, albo podmienia jedyny uchwyt, po czym Stop nie ma już czym dosięgnąć pierwszego procesu.
Ten task kończy rdzeń ownershipu oraz cienką krawędź transportu: jeden rejestr, adresowane
komendy, jedna wspólna pula i typowana koperta zdarzeń, którą aktualne okno potrafi odebrać.
Frontendowe karty wielu workspace'ów, routing między widokami, cache i eviction należą do T-204.

Jedynym źródłem prawdy jest:

`canonical workspace → LiveEntry { run_uuid, owner_terminal, control, lifecycle }`.

Jeden workspace ma najwyżej jeden aktywny Run albo `/ask`; różne workspace'y mogą pracować
równolegle. `run_uuid` rozróżnia generacje w tym samym folderze, `owner_terminal` mówi, kto może
prezentować i zamknąć bieg, `RunControl` zachowuje faktyczne ownership procesu, a `lifecycle`
rozróżnia oczekiwanie na globalny slot, pracę i cleanup bez dowodu śmierci. Settled nie jest
wariantem retencyjnym — po prawdziwym rozliczeniu wpis znika.

**Zależy od:** T-151, T-152, T-153, T-156, T-201, T-203 i T-210, który ląduje wspólny stos
T-202/T-210.

## Tryb wykonania — FULL HARNESS / large

- Jedyne wejście to `./ship-task.sh T-155 --agent codex --reviewer codex`; pisarz i read-only
  reviewer są osobnymi Codexami na różnych modelach. Nie uruchamiaj domyślnego Claude'a.
- Obowiązują uczciwe czerwone `before`, quick/full, jedna recenzja, najwyżej jedna naprawa i jedno
  `integrate.sh`. Exit 2, invalid oracle albo czerwień po naprawie zatrzymują pracę dla człowieka.
- Zakres frontu obejmuje wyłącznie lustro `RunPacket`, przekazanie pełnego adresu przez produkcyjne
  funkcje IO i istniejące oracles sygnatur. Każdy SHA po integracji zachowuje działający strumień
  i zgodne wywołania Tauri. Stan kart, routing paczek między widokami, cache i eviction należą do
  T-204; backend nie dostaje globalnego ani opcjonalnego fallbacku.
- Ciężkie Cargo biegnie pojedynczo na całej maszynie.

## Mandat na stare kontrakty singletonu

Wolno zmienić stare testy T-69/T-71/T-65 wyłącznie tak, aby ich fakt stał się scoped:

- start w **tym samym** workspace nie podmienia żywego uchwytu;
- start w innym workspace jest legalny;
- `ALREADY_GOING` pozostawia pending tylko dla zajętego workspace;
- zamknięcie terminalu bez biegu nie zatrzymuje sąsiedniego biegu;
- feed i sterowanie nadal należą do terminalu inicjującego, nie do każdej karty tego folderu.

Nie wolno usuwać asercji o braku osierocenia, dowodzie śmierci, trwałej akceptacji triggera
ani izolacji/historii otwartego terminalu. Cleanup-needed z T-152 pozostaje w rejestrze aż do
ESRCH; ten task jedynie nadaje jego ponownemu Stopowi właściwy adres.

## Kontrakt tożsamości i lifecycle

Manualny caller wybija UUID v7 istniejącą rustową mennicą bezpośrednio przed Startem; trigger
używa `claim.run_id`. Backend waliduje UUID, kanonizuje istniejący workspace i atomowo rezerwuje
wpis przed pierwszym procesem. Nie ma osobnej komendy „reserve" ani stanu, który może zostać
osierocony między rezerwacją i Startem.

Kanał Run niesie osobną kopertę
`RunPacket { identity: RunIdentity, physical_step_uuid: Option<Uuid>, lines: Vec<Line> }`.
`identity` jest w każdej paczce. `physical_step_uuid` ma na drucie wartość `null` dla zdarzeń
całego biegu i UUID dla zdarzeń fizycznego kroku; jedna paczka nie miesza różnych fizycznych
kroków. Pierwsza paczka legalnie może być run-level z `null`. `Line` i jego golden nie zmieniają
kształtu. Rozmowy nadal używają obecnego `wireChannel` z nagim `Line[]`, a Run dostaje osobny
`wireRunChannel` — nowa koperta nie może po cichu odciąć Lead/chat ani aktualnego okna.

`lifecycle` jest zamkniętym typem co najmniej
`Waiting | Running | CleanupNeeded | RecoveryUnknown`. Start czekający na globalny limiter nadal
rezerwuje swój workspace i daje się adresowanie anulować, ale nie ma PID ani nie udaje
uruchomionego procesu. `AppState` tworzy i posiada jedyny `Limiter`; rejestr
żywych biegów dostaje jego klonowalny uchwyt i nigdy nie tworzy drugiej puli. `Waiting` nie ma
permitu. Permit należy do uruchomionego fizycznego kroku, a po braku proofa do `OwnedSurvivor`
z T-201. `CleanupNeeded` zachowuje ten owner tranzytywnie. Cleanup starej generacji usuwa wpis
wyłącznie przez compare-with-run-UUID; nigdy nie usuwa nowszego biegu tego samego workspace.

Zgodnie z T-94 zaakceptowany Start może jawnie przestawić limit **tej jednej puli** wartością
`how_many_at_once`; późniejszy zaakceptowany Start jest ostatnią zmianą globalnego suwaka, nie
właścicielem drugiego limitu. Test używa różnych wartości i dowodzi wspólnego skutku zamiast
samego przypadku `2 == 2`.

## Uczciwe `before`

Wszystkie trzy Rustowe targety, frontendowy target i każdy nowy importowany moduł istnieją przed
`./verify.sh before`. Minimalne typy `RunIdentity`, `RunPacket`, `LiveEntry`, `LiveLifecycle`
oraz adresowane sygnatury komend są kompilowalne, a aktualne okno potrafi zebrać paczkę bez
collection error. Rust wywołuje produkcyjny `AppState`, realny globalny `Limiter`, prawdziwą
kanonizację temp repo i typowane wyniki T-201. Targety padają na asercji globalnej odmowy,
globalnego Stopu, utraty ownershipu po recovery albo odciętego okna. Brak symbolu, compile error,
zero testów, timeout i test samej mapy nie są czerwienią.

## AC-1 Rejestr jest kluczowany kanonicznym workspace i dzieli jedną pulę
check: cargo test --test t155_live_registry_is_keyed_by_workspace
expect: (\d+) passed

Dwa realne temp repo i blokujące fake-drivery startują przez te same wejścia, których używa
okno. Start A ustawia limit 2, późniejszy zaakceptowany Start B ustawia go na 3, a maksymalny
overlap całej aplikacji wynosi 3, nie 5 ani osobne 2/3 per workspace. Drugi start A jest
odrzucony, B przechodzi; symlink do A nadal jest A. Po rozliczeniu starego A nowy A startuje,
a cleanup starej generacji nie usuwa uchwytu nowej. Przy zajętej całej puli następny workspace
dostaje typowany stan Waiting i startuje po zwolnieniu slotu, bez busy-loopu.

`AppState` posiada dokładnie jeden `Limiter` i jeden rejestr żywego ownershipu. Settled wpis
znika; cleanup-needed nie znika bez ESRCH. Setki kolejnych, prawidłowo rozliczonych generacji
wracają do baseline'u mapy. Nie powstaje drugi rejestr ani drugi limiter schowany w module
workspace. Trigger B polluje i startuje, gdy A jest aktywny i pula ma wolny slot; nie dziedziczy
globalnego `busy` po A.

## AC-2 Stop, Continue, Say i Close trafiają do właściwego biegu
check: cargo test --test t155_run_commands_are_addressed
expect: (\d+) passed

Scena ma A czekające na decyzję i B pracujące. Continue A, Say do B oraz Stop B niosą folder +
run UUID i dotykają tylko właściwego `RunControl`; Stop A kończy A. Powtórzenie komendy ze starym
UUID po nowym biegu tego samego workspace jest odmową. Brak pełnego adresu odmawia także wtedy,
gdy żyje tylko jeden bieg; backend nigdy nie wybiera globalnego „pierwszego" ani „aktualnego".

`owner_terminal` jest częścią autorytetu Close: zamknięcie idle siblinga tego samego workspace
nie zatrzymuje niczego, a Close właściciela adresuje jego run UUID. Trigger i `/ask` dostają
własnego jawnego ownera, nie `None` interpretowane później jako „ktokolwiek". Brak workspace,
brak UUID, brak terminala albo niejednoznaczna/stara tożsamość zawsze odmawia; backend nie wybiera
„pierwszego" ani „aktualnego" wpisu.

Prawdziwy kanał każdego biegu dostarcza `RunPacket` z dokładnie tą samą `RunIdentity`, którą
przyjął Start. Zdarzenia fizycznego kroku niosą jego UUID, zdarzenia całego biegu `null`, a test
odrzuca paczkę bez tożsamości, ze zmienionym workspace/run UUID albo mieszającą dwa kroki.

## AC-3 Recovery zachowuje ownership aż do dowodu i nie retencjonuje settled
check: cargo test --test t155_live_registry_recovers_ownership
expect: (\d+) passed

Target podaje rejestrowi typowane wyniki T-201 zamiast powtarzać jego macierz sygnałów. `Settled`
i `Dead` nie zostawiają wpisu. `WaitingWithoutProcess` rozlicza się jako niewykonana/anulowana
próba i również nie zostawia wpisu. `OwnedSurvivor` przechodzi do `CleanupNeeded` z tym samym
workspace, run UUID, ownerem procesu, `RunControl` i zajętym slotem. Dopiero callback rozliczenia
z pasującym run UUID usuwa wpis; callback starej generacji nie może usunąć nowszego biegu.

Stary katalog/receipt bez `run.json`, `RunIdentity`, PID i PGID pozostaje wyłącznie historią:
nie tworzy `LiveEntry` i nie blokuje Startu. Typowany aktywny receipt z workspace/run UUID, lecz
bez rozstrzygalnego faktu procesu, staje się `RecoveryUnknown`: blokuje tylko ten workspace i
jest diagnostyką dla T-209, ale nie wymyśla PID/PGID, ownera procesu, permitu, `RunControl` ani
dowodu śmierci.

Zamknięcie aplikacji snapshotuje wpisy bez trzymania synchronicznego zamka przez `await` i woła
wspólną granicę Stop z T-201. Nie powtarza sekwencji TERM/KILL/ESRCH: wynik `Dead` rozlicza dany
wpis, a `OwnedSurvivor` zachowuje go do następnej adresowanej próby. Jedna grupa bez proofa nie
blokuje rozliczenia sąsiedniego workspace i nie tworzy drugiego rejestru ani limitera.

## AC-4 Adresowana paczka nie odcina aktualnego okna
check: npx --no-install vitest run src/sections/run/t155-addressed-packet-keeps-current-window-live.test.ts
expect: (\d+) passed

Target przechodzi przez produkcyjny Start, `src/sections/run/io.ts`, Tauri `Channel` i prawdziwy
sink aktualnego okna. Manualny Start wybija dokładnie jeden UUID v7 bezpośrednio przed
`run_workflow`; pełna `RunIdentity` jedzie w żądaniu, a zgodny `RunPacket` dochodzi do bieżącego
feedu jako jedna paczka i jedna aktualizacja. Stop, Continue, Say i Close wysyłają tę samą
tożsamość; stary lub niepełny adres nie dostaje frontendowego fallbacku.

Kontrola rozmowy przepuszcza dotychczasową nagą paczkę `Line[]` przez `wireChannel`, więc zmiana
Run nie odcina Lead/chat. Target nie tworzy wielu kart, cache ani routingu między workspace'ami —
te zachowania należą do T-204.
