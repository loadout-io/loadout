# T-155 — Jeden bieg na workspace, wiele workspace'ów naraz

T-24 i ARCHITECTURE obiecują aktywne biegi w kilku kartach, ale późniejsze T-69, T-71 i T-65
świadomie zatrzymały etap A: jeden globalny `AppState.live`. To zadanie realizuje opisany tam
etap B. Nie osłabia ochrony przed podmianą uchwytu — przenosi ją z aplikacji na kanoniczny
workspace.

Minimalny model to `RunIdentity { canonical_workspace, run_uuid } → owned RunControl`, z osobnym
`terminal_id` mówiącym, która karta prezentuje bieg. Nie powstaje druga maszyna stanów ani drugi
limiter. Jeden workspace nadal ma najwyżej jeden aktywny Run lub `/ask`, ale różne workspace'y
korzystają równolegle z jednej istniejącej puli aplikacji.

**Zależy od:** T-154; pozostałe zależności są tranzytywne.

**Read first:** `docs/ARCHITECTURE.md` §6a · `tasks/T-24.md`, `tasks/T-65.md`, `tasks/T-69.md`,
`tasks/T-71.md` · `AGENTS.md` niezmienniki 2, 6, 7, 11, 13 i 24 ·
`src-tauri/src/ipc.rs` (`AppState`, `begin_run`, `begin_a_run`, `stop_run`) ·
`src-tauri/src/commands/run.rs` (`continue_run_inner`, `say_to_agent_inner`) ·
`src-tauri/src/workspace.rs` · `src-tauri/src/engine/{limits,line}.rs` · typy IPC,
frontendowe karty, feed, AgentScreen i IO.

## Tryb wykonania

- **Agent:** Codex w osobnym worktree, bez `ship-task.sh`.
- **Druga opinia:** osobny Codex na innym modelu, read-only; właścicielski same-vendor D3.
- Wywołania: `./review.sh --agent codex --reviewer codex`, a jeśli są uwagi, dokładnie raz
  `./repair.sh --agent codex --reviewer codex`. Nie uruchamiaj domyślnego agenta Claude.
- Pełna ręczna pętla; ciężkie Cargo wyłącznie szeregowo.

## Mandat na stare kontrakty singletonu

Wolno zmienić stare testy T-69/T-71/T-65 wyłącznie tak, aby ich fakt stał się scoped:

- start w **tym samym** workspace nie podmienia żywego uchwytu;
- start w innym workspace jest legalny;
- `ALREADY_GOING` pozostawia pending tylko dla zajętego workspace;
- zamknięcie terminalu bez biegu nie zatrzymuje sąsiedniego biegu;
- feed i sterowanie nadal należą do terminalu inicjującego, nie do każdej karty tego folderu.

Nie wolno usuwać asercji o braku osierocenia, dowodzie śmierci, trwałej akceptacji triggera
ani izolacji/historii otwartego terminalu. Cleanup-needed z T-152 pozostaje w rejestrze aż do
ESRCH; ten task jedynie nadaje jego ponownemu Stopowi właściwy adres.

## Kontrakt tożsamości

Manualny frontend pobiera UUID v7 z istniejącej rustowej mennicy bezpośrednio przed wywołaniem
Start i przekazuje go jako argument; trigger używa już wybitego `claim.run_id`. Backend waliduje
UUID, kanonizuje workspace i atomowo rezerwuje parę przed pierwszym procesem — nie powstaje osobna
komenda rezerwacji ani osierocony stan „planned". Ta sama tożsamość trafia do planu i pierwszego
zdarzenia IPC oraz wszystkich kolejnych komend. Stop, Continue, Say, retry, resume, `/ask`, trigger
i close używają jej konsekwentnie. Brakująca, stara albo niejednoznaczna tożsamość jest odmową;
backend nigdy nie wybiera „aktualnego" globalnego biegu.

## Uczciwe `before`

Dwa Rustowe targety wywołują produkcyjny `AppState`, nie sam limiter. Dwa frontendowe targety
montują prawdziwe karty/AgentScreen. Szkielety nowych adresowanych wejść istnieją przed `before`;
testy padają na globalnej odmowie, globalnym Stopie albo złym cache key, nie na braku symbolu.

## AC-1 Dwa workspace'y pracują, ale dzielą jedną pulę
check: cargo test --test t155_live_runs_are_keyed_by_workspace
expect: (\d+) passed

Dwa realne temp repo i blokujące fake-drivery startują przez te same wejścia, których używa
okno. Przy globalnym limicie 2 maksymalny overlap wynosi 2 łącznie, nie 4. Drugi start A jest
odrzucony, B przechodzi; symlink do A nadal jest A. Po rozliczeniu starego A nowy A startuje,
a cleanup starej generacji nie usuwa uchwytu nowej. Przy zajętej całej puli następny workspace
dostaje typowany stan Waiting i startuje po zwolnieniu slotu, bez busy-loopu.

Rejestr używa kanonicznej ścieżki i istniejącego globalnego `Limiter`. Settled wpis znika;
cleanup-needed wpis nie znika bez ESRCH, a mapa nie może stać się nową retencją po prawdziwym
settle. Martwy produkcyjnie `workspace::Registry` zostaje albo
włączony jako jedno źródło tożsamości, albo usunięty — nie zostają dwa rejestry folderów.
Trigger B polluje i startuje, gdy A jest aktywny, ale globalna pula nadal ma wolny slot; nie
dziedziczy globalnego `busy` po A.

## AC-2 Stop, Continue, Say i Close trafiają do właściwego biegu
check: cargo test --test t155_workspace_stop_is_addressed
expect: (\d+) passed

Scena ma A czekające na decyzję i B pracujące. Continue A, Say do B oraz Stop B niosą folder +
run UUID i dotykają tylko właściwego `RunControl`; Stop A kończy A. Powtórzenie komendy ze starym
UUID po nowym biegu tego samego workspace jest odmową. Brak adresu przy więcej niż jednym biegu
również odmawia, nigdy nie wybiera globalnego „pierwszego".

Dwa terminale tego samego workspace mają jeden bieg, lecz wyłącznie terminal inicjujący dostaje
feed i kontrolki. Zamknięcie idle siblinga niczego nie zatrzymuje; zamknięcie właściciela adresuje
jego bieg. Zamknięcie aplikacji zatrzymuje wszystkie żywe grupy, czeka na każdy dowód i zachowuje
osobne PID/PGID dla ocalałych. Dla `cleanup-needed` z T-152 ponowny Stop pozostaje widoczny,
trafia do tej samej grupy Alive, a dopiero kontrolowane `Dead` usuwa wpis i permit.

## AC-3 Człowiek widzi i zatrzymuje oba biegi niezależnie
check: npx --no-install vitest run e2e/tests/t155-two-workspaces-run-independently.spec.ts
expect: (\d+) passed

Spec otwiera A, startuje bieg, przełącza na B i startuje drugi. Obie karty mają własną live dot,
feed i liczbę agentów; powrót do A pokazuje wszystkie jego linie. Osobna scena z pełną pulą
pokazuje na C angielskie Waiting, a potem automatyczny start po zwolnieniu slotu. Stop B wysyła
folder B i UUID B, usuwa wyłącznie jego stan żywy, a A nadal postępuje.

Istniejący browser harness dostaje wyłącznie małą krawędź `emit` do dostarczenia typowanej paczki
na `Channel`, bez implementowania polityki Rusta. Rustowe AC-1/2 dowodzą adresowania backendu;
ten spec dowodzi, że prawdziwe kliknięcia i callbacki rozdzielają dwa widoki.

Spec otwiera też drugi terminal wskazujący ten sam folder A: nie duplikuje na nim feedu ani
kontrolek i jego zamknięcie nie zatrzymuje A. Globalne `going` nie może zostać w module; zapadka
jest per workspace/run, a prezentacja per terminal.

## AC-4 Kontekst ekranu jest kluczowany biegiem i fizycznym krokiem
check: npx --no-install vitest run src/sections/run/session/t155-context-is-keyed-by-run-and-step.test.tsx
expect: (\d+) passed

Target kontroluje kolejność Promise. Odczyt A startuje, potem B; B kończy pierwszy, A ostatni,
a prawdziwy `AgentScreen` pozostaje przy B bez handoffów/notatek A. Druga scena uruchamia nowy
run w tym samym folderze i powtarza nazwę kafelka w dwóch kopiach: wynik starego runu ani
fizycznego step UUID nie może nadpisać nowego. Błąd bieżącego żądania daje pusty bieżący stan,
nie cache poprzednika. Klucz to terminal + canonical folder + run UUID + physical step UUID.
