# T-155 — Backend adresuje żywe biegi kanonicznym workspace i UUID

T-24 i ARCHITECTURE obiecują aktywne biegi w kilku workspace'ach, ale produkcyjny `AppState`
ma jeden globalny `live: RunControl`. Drugi poprawny Start albo odmawia dlatego, że pracuje inny
folder, albo podmienia jedyny uchwyt, po czym Stop nie ma już czym dosięgnąć pierwszego procesu.
Ten task kończy rdzeń ownershipu i wszystkie produkcyjne krawędzie komend: jeden rejestr,
adresowane Start/Ask/rerun/resume/Stop/Continue/Say/Close, jedna wspólna pula oraz typowana
koperta zdarzeń. Aktualne okno zachowuje działający feed i kontrolki. T-204 nie wybija ponownie
UUID ani nie rekonstruuje adresu; dostaje gotowy adres i odpowiada wyłącznie za routing między
kartami, cache kontekstu i eviction zamkniętego stanu.

Jedynym źródłem prawdy żywego sterowania jest mapa:

`canonical workspace → LiveEntry { address, control, lifecycle }`, gdzie:

- `RunIdentity { canonical_workspace, run_uuid }` nazywa jedną generację biegu;
- tagowany `RunOwner` ma dokładnie warianty `Terminal { terminal_id }` oraz
  `Trigger { slug, delivery_id }`;
- `RunAddress { identity, owner }` jest pełnym adresem każdej późniejszej komendy;
- `LiveLifecycle` ma dokładnie `Accepted | Waiting | Running | CleanupNeeded`.

Jeden workspace ma najwyżej jeden aktywny Run albo `/ask`; różne workspace'y mogą pracować
równolegle. `run_uuid` rozróżnia generacje w tym samym folderze, owner mówi, kto może
prezentować i zamknąć bieg, `RunControl` zachowuje faktyczne ownership procesu, a lifecycle
rozróżnia atomową akceptację, oczekiwanie na globalny slot, pracę i cleanup bez dowodu śmierci.
Settled nie jest wariantem retencyjnym — po prawdziwym rozliczeniu wpis znika. Historyczne
odtwarzanie nie rozszerza tej mapy; jest wyłączną odpowiedzialnością T-209.

**Zależy od:** T-151, T-152, T-153, T-156, T-201, T-203 i T-210, który ląduje wspólny stos
T-202/T-210.

## Tryb wykonania — FULL HARNESS / large

- Jedyne wejście to `./ship-task.sh T-155 --agent codex --reviewer codex`; pisarz i read-only
  reviewer są osobnymi Codexami na różnych modelach. Nie uruchamiaj domyślnego Claude'a.
- Obowiązują uczciwe czerwone `before`, quick/full, jedna recenzja, najwyżej jedna naprawa i jedno
  `integrate.sh`. Exit 2, invalid oracle albo czerwień po naprawie zatrzymują pracę dla człowieka.
- Zakres frontu obejmuje lustro `RunPacket`, wybicie żądania, zachowanie zwróconego adresu oraz
  przekazanie go przez wszystkie faktyczne callery. Każdy SHA po integracji zachowuje działający
  strumień i zgodne wywołania Tauri. Wielokartowy routing paczek, cache kontekstu i eviction
  należą do T-204; T-155 przygotowuje dla nich gotowy adres i zdarzenie zamknięcia, ale nie
  implementuje drugiej polityki prezentacji. Backend nie dostaje globalnego ani opcjonalnego
  fallbacku.
- Ciężkie Cargo biegnie pojedynczo na całej maszynie.

## Mandat na stare kontrakty singletonu

Wolno zmienić stare testy T-69/T-71/T-65 wyłącznie tak, aby ich fakt stał się scoped:

- start w **tym samym** workspace nie podmienia żywego uchwytu;
- start w innym workspace jest legalny;
- `ALREADY_GOING` pozostawia pending tylko dla zajętego workspace;
- zamknięcie terminalu bez biegu nie zatrzymuje sąsiedniego biegu;
- feed i sterowanie nadal należą do terminalu inicjującego, nie do każdej karty tego folderu.

Nie wolno usuwać asercji o braku osierocenia, dowodzie śmierci, trwałej akceptacji triggera
ani izolacji/historii otwartego terminalu. Cleanup-needed z T-152 pozostaje w rejestrze aż do
ESRCH; ten task jedynie nadaje jego ponownemu Stopowi właściwy adres.

## Kontrakt żądania, adresu i lifecycle

Każda ręczna droga tworząca nowy żywy bieg — przycisk Start, `/run`, `/ask`, rerun i resume —
wybija dokładnie jeden UUID v7 istniejącą rustową mennicą bezpośrednio przed IPC. Wysyła
`StartRequest { folder, run_uuid, owner: Terminal { terminal_id }, ... }`: `folder` jest ścieżką
żądaną przez okno, nie rzekomo kanoniczną tożsamością. Trigger nie ufa ownerowi z webviewa:
backend bierze `run_uuid` z już zweryfikowanego `claim.run_id` i konstruuje
`Trigger { slug, delivery_id }` z durable claimu. Trigger nie jest ukrytym terminalem i nie
dostaje pustego `terminal_id`.

Backend waliduje UUID, kanonizuje istniejący workspace i atomowo rezerwuje wpis przed pierwszym
procesem. Nie ma osobnej komendy `reserve` ani stanu, który może zostać osierocony między
rezerwacją i Startem. Pierwszy `RunPacket` po akceptacji zwraca autorytatywne
`RunIdentity { canonical_workspace, run_uuid }` oraz tego samego ownera; dopiero z nich frontend
zapamiętuje `RunAddress`. Okno nie kanonizuje ścieżki samo, nie wysyła fikcyjnej pełnej
`RunIdentity` przed odpowiedzią i nie rekonstruuje adresu z aktualnie wybranej karty. Po wydaniu
adresu lookup używa dokładnie klucza backendu — nie kanonizuje go ponownie, gdy folder zniknął,
symlink zmienił cel albo cleanup wymaga jeszcze Stopu.

Kanał Run niesie osobną kopertę
`RunPacket { identity, owner, lifecycle, physical_step_uuid, lines }`. Pierwsza paczka jest
run-level (`physical_step_uuid: null`) i ogłasza `Accepted` przed pierwszym procesem; jeśli bieg
nie ma jeszcze miejsca w puli, kolejna zmiana to `Waiting`, a nie drugi Start ani nowy UUID.
`Running` oznacza faktycznie rozpoczętą pracę, `CleanupNeeded` — zachowany owner bez dowodu
śmierci. Osobna terminalna paczka rozliczenia usuwa pasujący wpis, ale `Settled` nie staje się
stanem mapy. Każda paczka powtarza ten sam adres. `physical_step_uuid` ma `null` dla zdarzeń
całego biegu i UUID dla zdarzeń jednego fizycznego kroku; jedna paczka nie miesza kroków, a
logical step id ani nazwa kafelka nie zastępują fizycznego UUID. `Line` i jego golden nie
zmieniają kształtu. Rozmowy nadal używają obecnego `wireChannel` z nagim `Line[]`, a Run dostaje
osobny `wireRunChannel` — nowa koperta nie może odciąć Lead/chat ani aktualnego okna.

`AppState` tworzy i posiada jedyny `Limiter`; rejestr żywych biegów dostaje jego klonowalny
uchwyt i nigdy nie tworzy drugiej puli. `Waiting` nie ma permitu i czeka na wakeup istniejącego
semafora, bez pollingu i busy-loopu. Permit należy do uruchomionego fizycznego kroku, a po braku
proofa do `OwnedSurvivor` z T-201. `CleanupNeeded` zachowuje ten owner tranzytywnie. Cleanup
starej generacji usuwa wpis wyłącznie przez compare-with-run-UUID; nigdy nie usuwa nowszego
biegu tego samego workspace.

Frontend nie czyści zaakceptowanego adresu, feedu, live dot ani kontrolek dlatego, że future
komendy się rozwiązał lub wszedł w `finally`. Może wycofać lokalny szkic po odmowie przed
rezerwacją albo usunąć pasujący adres po terminalnej paczce backendu. Po `CleanupNeeded` karta,
adresowany Retry Stop i diagnostyka pozostają osiągalne aż do pasującego `Dead`; późny `finally`
starej generacji nie może usunąć nowszej.

Ponieważ T-155 jest jedynym writerem produkcyjnych callerów i bazowych magazynów, zostawia
T-204 dwie gotowe, wąskie krawędzie: odczyt pełnego adresu dla terminalu/runu oraz zdarzenie
`terminal closed/settled` z generation. Bazowy store potrafi usunąć pasujący run po tym
zdarzeniu, ale T-155 nie zna cache handoffów, kontekstu, procesów ani feedów innych kart. T-204
subskrybuje tę krawędź i ewakuuje własne rejestry bez ponownej zmiany plików callerów.

Zgodnie z T-94 zaakceptowany Start może jawnie przestawić limit **tej jednej puli** wartością
`how_many_at_once`; późniejszy zaakceptowany Start jest ostatnią zmianą globalnego suwaka, nie
właścicielem drugiego limitu. Start odrzucony przed rezerwacją nie zmienia suwaka. Test używa
różnych wartości i dowodzi wspólnego skutku zamiast samego przypadku `2 == 2`.

Istniejący `workspace::Registry` może nadal modelować niezależną listę/zakres kart albo pozostać
testowym helperem. T-155 nie usuwa go „dla porządku" i nie przebudowuje, jeśli nie steruje żywym
procesem. Wspólny ma być prymityw `WorkspaceId`/kanonizacji, a zakaz drugiego rejestru dotyczy
wyłącznie drugiej mapy live-control lub drugiego limitera w runtime `AppState`.

Stop, Continue i Say przyjmują dokładny `RunAddress`. Tauri wrapper może przyjąć
`Option<RunAddress>` wyłącznie po to, by wejść do ciała komendy i zwrócić widoczną angielską
odmowę dla starego callera; `None` nigdy nie wybiera jedynego, pierwszego ani aktualnego biegu.
`close_terminal` może nie mieć adresu tylko wtedy, gdy terminal nie jest ownerem żadnego żywego
biegu; zamknięcie ownera niesie pełny adres, a idle sibling nie zatrzymuje sąsiada. Zamknięcie
całej aplikacji jest osobną wewnętrzną operacją `stop-all` na snapshotcie mapy, nigdy publicznym
fallbackiem komendy bez adresu.

## Uczciwe `before`

Wszystkie trzy Rustowe targety, frontendowy target i każdy nowy importowany moduł istnieją przed
`./verify.sh before`. Minimalne typy `StartRequest`, `RunIdentity`, `RunOwner`, `RunAddress`,
`RunPacket`, `LiveEntry` i `LiveLifecycle` oraz adresowane sygnatury komend są kompilowalne, a
aktualne okno potrafi zebrać paczkę bez collection error.

- AC-1 najpierw dowodzi starej globalnej odmowy: blokujący A działa, poprawny Start B przez
  produkcyjny `AppState` zostaje odrzucony wyłącznie dlatego, że istnieje A. Dopiero dalsze sceny
  rozszerzają oracle na wspólny limiter, alias i Waiting.
- AC-2 zaczyna od jednego żywego biegu oraz starego/złego UUID. Dzisiejszy globalny Stop dotyka
  tego biegu mimo niepasującego adresu, więc uczciwa czerwień nie zakłada jeszcze działających
  dwóch biegów. Potem ten sam target dowodzi rozdzielenia A/B i wszystkich komend.
- AC-3 wywołuje produkcyjny `AppState` i typowany wynik T-201, nie helper mapy ani historyczny
  stan recovery należący do T-209.
- AC-4 przechodzi przez prawdziwe `launchRun`, `/ask`, rerun, resume oraz produkcyjne callery
  Stop/Continue/Say/Close. Nie woła samych wrapperów IO i nie podaje komponentowi adresu, którego
  produkcyjna droga jeszcze nie ma.

Barierami i kontrolowanym semaforem mierzy się Waiting/overlap; timeout nie jest oracle. Targety
padają na asercji globalnej odmowy, globalnego Stopu, przedwczesnego zwolnienia ownershipu albo
nieadresowanego callera. Brak symbolu, compile error, zero testów, collection error, timeout i
test samej mapy nie są czerwienią.

## AC-1 Rejestr jest kluczowany kanonicznym workspace i dzieli jedną pulę
check: cargo test --test t155_live_registry_is_keyed_by_workspace
expect: (\d+) passed

Dwa realne temp repo i blokujące fake-drivery startują przez te same wejścia, których używa
okno. Pierwsza scena zatrzymuje A i dowodzi, że bieżący singleton błędnie odmawia poprawnego B.
Po implementacji Start A ustawia limit 2, późniejszy zaakceptowany Start B ustawia go na 3, a
maksymalny overlap całej aplikacji wynosi 3, nie 5 ani osobne 2/3 per workspace. Start odrzucony
przed rezerwacją nie przestawia limitu. Drugi start A jest odrzucony, B przechodzi; symlink do A
nadal jest A. Po rozliczeniu starego A nowy A startuje, a cleanup starej generacji nie usuwa
uchwytu nowej. Przy zajętej całej puli następny workspace dostaje najpierw ten sam kanoniczny
adres w paczce `Accepted`, potem typowany `Waiting` i startuje po wakeupie slotu, bez pollingu,
busy-loopu ani wybicia nowego UUID.

`AppState` posiada dokładnie jeden `Limiter` i jeden rejestr żywego ownershipu. Settled wpis
znika; cleanup-needed nie znika bez ESRCH. Setki kolejnych, prawidłowo rozliczonych generacji
wracają do baseline'u mapy. Oracle obserwuje zachowanie produkcyjnego `AppState`, nie grepuje
`Limiter::new` w niezależnym testowym `workspace::Registry` i nie usuwa tego typu. Druga mapa
live-control ani druga pula nie powstają. Trigger B polluje i startuje, gdy A jest aktywny i
pula ma wolny slot; nie dziedziczy globalnego `busy` po A. Gdy pula jest pełna, pozostaje
typed transient/pending zgodnie z T-65, bez frontendowej polityki retry.

## AC-2 Stop, Continue, Say i Close trafiają do właściwego biegu
check: cargo test --test t155_run_commands_are_addressed
expect: (\d+) passed

Pierwsza scena ma jeden żywy A i wysyła Stop ze starym/złym UUID. Dzisiejszy globalny Stop
błędnie dotyka A; po zmianie komenda odmawia i A nadal pracuje. Pełna scena ma A czekające na
decyzję i B pracujące. Continue A, Say do B oraz Stop B niosą dokładny `RunAddress` i dotykają
tylko właściwego `RunControl`; Stop A kończy A. Powtórzenie komendy ze starym UUID po nowym biegu
tego samego workspace jest odmową. Brak pełnego adresu odmawia także wtedy, gdy żyje tylko jeden
bieg; backend nigdy nie wybiera globalnego „pierwszego" ani „aktualnego".

`Terminal { terminal_id }` jest częścią autorytetu Close: zamknięcie idle siblinga tego samego
workspace nie zatrzymuje niczego, a Close ownera adresuje jego dokładny run UUID. `/ask` dostaje
terminalowego ownera, trigger `Trigger { slug, delivery_id }`; żaden nie używa `None`
interpretowanego później jako „ktokolwiek". Brak workspace, UUID lub ownera albo
niejednoznaczna/stara tożsamość zawsze odmawia. Zamknięcie całej aplikacji używa jawnego
wewnętrznego stop-all na snapshotcie wszystkich wpisów, a nie publicznego Stop bez adresu.

Prawdziwy kanał każdego biegu dostarcza pierwszy `RunPacket` z kanoniczną `RunIdentity` wyliczoną
przez backend oraz ownerem z zaakceptowanego requestu. Każda kolejna paczka zachowuje ten adres.
Zdarzenia fizycznego kroku niosą jego UUID, zdarzenia całego biegu `null`, a test odrzuca paczkę
bez tożsamości/ownera, ze zmienionym workspace/run UUID albo mieszającą dwa kroki.

## AC-3 Żywy ownership trwa do dowodu i nie retencjonuje settled
check: cargo test --test t155_live_registry_recovers_ownership
expect: (\d+) passed

Target podaje rejestrowi typowane wyniki T-201 zamiast powtarzać jego macierz sygnałów. `Settled`
i `Dead` nie zostawiają wpisu. `WaitingWithoutProcess` rozlicza się jako niewykonana/anulowana
próba i również nie zostawia wpisu. `OwnedSurvivor` przechodzi do `CleanupNeeded` z tym samym
workspace, run UUID, ownerem procesu, `RunControl` i zajętym slotem. Dopiero callback rozliczenia
z pasującym run UUID usuwa wpis; callback starej generacji nie może usunąć nowszego biegu.

Każdy historyczny katalog lub receipt — również stare wpisy o stanie `unknown`, bez `run.json`,
`RunIdentity`, PID albo PGID — pozostaje wyłącznie historią: nie tworzy `LiveEntry` i nie blokuje
Startu. T-155 nie wprowadza stanu live dla niepewnej recovery, nie skanuje dawnych runów i nie
zgaduje żywego ownershipu z niepełnego receipt. Jedynym właścicielem klasyfikacji oraz
bezpiecznej recovery po restarcie jest T-209.

Zamknięcie aplikacji snapshotuje wpisy bez trzymania synchronicznego zamka przez `await` i woła
wspólną granicę Stop z T-201. Nie powtarza sekwencji TERM/KILL/ESRCH: wynik `Dead` rozlicza dany
wpis, a `OwnedSurvivor` zapisuje `CleanupNeeded` z pełnym PID/PGID i adresem do durable receipt
przed zniszczeniem okna. Rejestr in-memory nie udaje, że przeżywa nowy proces aplikacji; T-209
później rozstrzyga ten zapis. Jedna grupa bez proofa nie blokuje rozliczenia sąsiedniego
workspace i nie tworzy drugiego rejestru ani limitera.

## AC-4 Adresowana paczka nie odcina aktualnego okna
check: npx --no-install vitest run src/sections/run/t155-addressed-packet-keeps-current-window-live.test.ts
expect: (\d+) passed

Target przechodzi osobno przez produkcyjny `launchRun`, `/ask`, rerun i resume, a następnie przez
prawdziwe callery Stop, Continue, Say i Close. Każda ręczna droga wybija dokładnie jeden UUID v7
bezpośrednio przed właściwym IPC i wysyła `StartRequest` z żądanym folderem oraz
`Terminal { terminal_id }`. Nie wysyła rzekomo kanonicznego workspace. Pierwszy `RunPacket`
zwraca kanoniczną `RunIdentity`; frontend składa z niej oraz ownera jeden `RunAddress`, zachowuje
go przy bieżącym runie i używa bez zmian we wszystkich kontrolkach.

Paczka dochodzi przez `src/sections/run/io.ts`, Tauri `Channel` i prawdziwy sink aktualnego okna
jako jedna paczka i jedna aktualizacja. `Accepted`, `Waiting`, `Running`, fizyczny step UUID oraz
`CleanupNeeded` przeżywają transport. Rozwiązanie future albo jego `finally` nie usuwa
zaakceptowanego adresu po `CleanupNeeded`; dopiero pasująca terminalna paczka/`Dead` czyści stan.
Stary lub niepełny adres nie dostaje frontendowego fallbacku, a późny cleanup starego UUID nie
czyści nowszej generacji.

Kontrola rozmowy przepuszcza dotychczasową nagą paczkę `Line[]` przez `wireChannel`, więc zmiana
Run nie odcina Lead/chat. Target używa jednej widocznej karty naraz; nie dowodzi przełączania
dwóch widoków, cache kontekstu ani eviction — te zachowania należą do T-204.
