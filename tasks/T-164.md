# T-164 — Workflow należy do workspace, w którym będzie uruchomiony

Biblioteka workflow jest dziś globalna (`~/.loadout/workflows`). Po przełączeniu workspace
człowiek nadal widzi te same pliki, a CRUD, `/run`, Lead, historia, trigger i importer rozwiązują
nazwę przez ten sam globalny katalog. To przeczy podstawowemu modelowi aplikacji: workflow opisuje
pracę w konkretnym repozytorium i nie może po cichu przejść do sąsiedniej karty.

Kanoniczne miejsce to `<zarejestrowany workspace>/.loadout/workflows/<fileName>`. Agenci, Skills,
Connections i globalne Settings pozostają w `~/.loadout`; ten task nie przenosi ich do projektu.
Folder zawsze rozwiązuje Rust z rejestru workspace. Webview nie podaje dowolnej ścieżki docelowej,
a brak aktywnego/zarejestrowanego workspace daje widoczną odmowę — nigdy fallback do cwd ani do
starej biblioteki globalnej.

Stare workflow nie znikają i nie są przenoszone automatycznie. W pustej bibliotece workspace
Loadout pokazuje jedną jawną akcję `Copy existing workflows to this workspace`. Kopia jest
transakcyjna, nie nadpisuje konfliktu i zostawia oryginały w `~/.loadout/workflows` jako źródło
migracji. Dzięki temu wybór projektu nie jest zgadywany za człowieka.

**Zależy od:** T-163, T-209 oraz T-76, T-78 i T-82. Najpierw stabilizujemy Settings/Lead,
historyczne izolacje i pełny model importu; wszystkie te zadania przecinają IPC, Run, historię
albo importer.

## Tryb wykonania

- Codex w osobnym worktree, bez nowego Harnessu.
- Uczciwe czerwone `before`, quick/full i read-only review.
- Ciężkie Rustowe targety biegną szeregowo względem innych tasków.
- Jedna ścieżka scope w Ruście; adaptery UI przekazują identyfikator workspace, nie składają path.

## Uczciwe `before`

Rustowe targety zakładają dwa prawdziwe katalogi i rejestrują je przez produkcyjną granicę.
Frontendowy target montuje prawdziwą aplikację z opóźnianymi odpowiedziami IPC. Każdy moduł
istnieje przed `before`; porażka następuje na globalnym przecieku albo braku zachowania.

## AC-1 Dwa workspace mają dwie niezależne biblioteki
check: cargo test --test t164_workflows_belong_to_registered_workspace
expect: (\d+) passed

Zapis, odczyt, lista, walidacja, duplikacja i usunięcie tej samej nazwy w dwóch zarejestrowanych
workspace dotykają wyłącznie odpowiednich `<workspace>/.loadout/workflows`. Próba użycia folderu
spoza rejestru, `..`, symlinka wychodzącego poza workspace albo `null` jest odrzucona przed IO.
Usunięcie `loadout.db` nie zmienia wyniku. Globalne biblioteki agentów, Skills i Connections są
nadal wspólne i walidator obsady czyta je z `~/.loadout`.

## AC-2 Przełączenie workspace nie pokazuje spóźnionej cudzej listy
check: npx --no-install vitest run e2e/tests/t164-workflow-library-follows-workspace.spec.ts
expect: (\d+) passed

Chromium montuje aplikację z workspace A i B, w obu z workflow o innych nazwach. Po przełączeniu
A → B opóźniona odpowiedź listy A nie może zastąpić listy B ani otwartego dokumentu. Create,
Duplicate, Save i Delete wysyłają identyfikator aktualnego workspace dokładnie raz. Bez wyboru
ekran mówi po angielsku, że najpierw trzeba wybrać workspace, i nie rysuje aktywnej kontrolki CRUD.

## AC-3 Każda droga uruchomienia czyta workflow z workspace biegu
check: cargo test --test t164_every_run_path_uses_workspace_workflow
expect: (\d+) passed

Ta sama nazwa pliku ma inne grafy w A i B. Manual Run, `/run`, przycisk z edytora, rerun/pick-up
z historii i propozycja Lead uruchamiają graf z przypiętego workspace — także po przełączeniu
widocznej karty w trakcie rozmowy. `run.json` zachowuje wystarczający adres pliku, żeby historia
i wznowienie nie pytały dzisiejszej aktywnej karty. Brak pliku w tym workspace daje ludzki błąd;
globalny plik o tej samej nazwie nie jest fallbackiem.

## AC-4 Trigger jest związany z workspace i nie odpala imiennika
check: cargo test --test t164_trigger_resolves_workflow_in_its_workspace
expect: (\d+) passed

Zapis triggera wiąże go z jednym zarejestrowanym workspace. Poll, Retry i restart rozwiązują
workflow wyłącznie pod tym adresem; identyczny slug w sąsiednim workspace nie może zostać
uruchomiony. Usunięty workspace lub workflow przechodzi przez typowaną odmowę T-206 i nie jest
próbowany bez końca. Sekcja Triggers pokazuje nazwę workspace przy wierszu.

## AC-5 Import i migracja zapisują do jawnie wybranego workspace
check: cargo test --test t164_import_and_legacy_copy_are_workspace_scoped
expect: (\d+) passed

Apply importu bierze workspace z zatwierdzonego planu i zapisuje workflow pod jego `.loadout`,
po ponownym skanie źródła oraz z receiptami T-78. `Copy existing workflows to this workspace`
kopiuje wszystkie poprawne globalne pliki jako jedną transakcję, odmawia całości przy konflikcie,
nie dereferencjonuje symlinków poza starą bibliotekę i nie kasuje ani nie zmienia oryginałów.
Awaria po dowolnym pliku zostawia docelową bibliotekę byte-for-byte jak przed próbą.
