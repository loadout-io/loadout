# T-06 — Magazyn: schemat SQLite, jeden pisarz, migracje, wyzwalacze append-only

`loadout.db` jest **indeksem, nie prawdą**, i cała wartość tego podsystemu leży w jednym zdaniu:
wolno go skasować i nic się nie stanie (ARCHITECTURE §2 pyt. 2, niezmiennik 4). Cichy tryb porażki
jest dokładnie taki: ktoś zapisuje jedno pole, którego nie ma w żadnym pliku — koszt kroku,
podsumowanie dla szyny, kolejność zdarzeń — i przez trzy tygodnie wszystko działa, bo nikt bazy nie
kasuje. W dniu, w którym ktoś ją skasuje, ta wiedza znika, a wtedy `store/` już nie jest indeksem i
mamy poprzedniego prototypu z jego czterema migracjami schematu w dwudniowym repo. Drugi cichy tryb: „append-only"
egzekwowane w Ruście zamiast w SQLite — wystarczy jedno połączenie, które nie przechodzi przez nasze
API (migracja, skrypt naprawczy, przyszły daemon, `sqlite3` z terminala) i historia daje się
przepisać, a wszystkie nasze testy dalej są zielone, bo testowały nasze API. Trzeci: `busy_timeout`
ustawiony na połączeniu pisarza i zapomniany na czytającym — objawia się jako losowe „Save failed"
raz na dwa dni i w meetnotes zajęło to dwóch pisarzy w tle, zanim ktoś zrozumiał, co się dzieje
[00-SYNTHESIS §3, „SQLite"].

## Niezmienniki

- **2 — do SQLite pisze wyłącznie `store::writer`.** Drugie połączenie zapisujące to zakleszczenie,
  nie „czasem wolniej" [T7 ryzyko 7]. Łamie się cicho tak: funkcja czytająca dostaje
  `Connection::open(path)` „bo tak prościej", działa miesiąc w testach jednowątkowych i wykłada się
  dopiero przy dwóch agentach naraz — czyli w jedynym scenariuszu, dla którego ten produkt istnieje.
- **4 — pliki są prawdą, SQLite jest indeksem.** Każda kolumna musi dać się odtworzyć z
  `<repo>/.loadout/runs/<ts>__<id>/{run.json,logs/,handoffs/}`. Łamie się cicho tak: `steps.summary`
  albo `steps.cost_usd` jest zapisywane wyłącznie do bazy w trakcie biegu i nigdy nie ląduje w
  `run.json`. Nic nie krzyczy. AC-4 jest jedynym miejscem, w którym to wychodzi.
- **25 — migracje są addytywne i idempotentne.** `CREATE TABLE IF NOT EXISTS` +
  `add_column_if_missing`; `DROP`, `ALTER … DROP COLUMN` i przepisywanie wierszy są zakazane. Łamie
  się cicho tak: `ALTER TABLE … ADD COLUMN` bez sprawdzenia obecności — drugi start aplikacji rzuca
  `duplicate column name`, a użytkownik widzi „nie udało się otworzyć projektu".
- **19 — kod wyjścia to nie dowód.** Test, który tylko sprawdza, że `migrate()` zwróciło `Ok`, nie
  wie nic o schemacie. Każde kryterium niżej porównuje **stan**, nie kod powrotu.

## Kryteria akceptacji

## AC-1 `migrate()` wywołane dwa razy na tym samym połączeniu nie zmienia niczego
check: cargo test --test store_migrate_idempotent

Na połączeniu `:memory:`: `migrate()` → zrzut `SELECT type, name, tbl_name, sql FROM sqlite_master
ORDER BY type, name` → wstaw jeden wiersz do `runs` i jeden do `events` → `migrate()` **drugi raz**
→ zrzut ponownie. Asercje: oba zrzuty są **identyczne** (łącznie z treścią `sql` każdego wyzwalacza
i indeksu), drugie wywołanie zwraca `Ok`, a oba wstawione wiersze dalej są na miejscu z tymi samymi
wartościami wszystkich kolumn.

*Słaba asercja:* `assert!(migrate(&c).is_ok()); assert!(migrate(&c).is_ok())`. Przechodzi, dopóki
migracja składa się z samych `CREATE TABLE IF NOT EXISTS` — i przestaje w dniu, w którym ktoś doda
`ALTER TABLE steps ADD COLUMN`, bo `Ok` z pierwszego przebiegu nie mówi nic o drugim. Dyskryminuje:
porównanie **pełnego zrzutu `sqlite_master`** przed i po (łapie zmieniony wyzwalacz, zgubiony indeks
i przepisaną tabelę) oraz przeżycie wierszy wstawionych **pomiędzy** wywołaniami (łapie migrację,
która „naprawia" dane).

## AC-2 Wyzwalacze append-only łapią połączenie, które omija nasze API
check: cargo test --test store_append_only

Baza w pliku (`tempfile`). Przez `store::writer` wstaw 3 zdarzenia. Potem test otwiera **własne,
zapisujące** `rusqlite::Connection` prosto na tym pliku — z pominięciem całego naszego Rusta — i
próbuje: (a) `UPDATE events SET body='x' WHERE seq=1` → `Err`, komunikat zawiera tekst z `RAISE`
wyzwalacza; (b) `DELETE FROM events WHERE seq=1` → `Err`; (c) kontrola dodatnia na **tym samym**
połączeniu: `UPDATE runs SET status='succeeded'` → `Ok` i `INSERT INTO events …` → `Ok`
(`events` rośnie, `runs` i `steps` są z założenia mutowalne [T7 §5.1]); (d) `SELECT count(*) FROM
events` = 4 i `body` wiersza 1 nie zmienił się.

*Słaba asercja:* test, w którym próba `UPDATE` idzie przez nasze API i dostaje odmowę z Rusta.
Przechodzi na bazie bez jednego wyzwalacza — a wtedy pierwszy skrypt, przyszły daemon albo
`sqlite3 loadout.db` przepisze historię i nikt się nie dowie. Dyskryminuje: połączenie otwarte
**bezpośrednio** w teście, z prawem zapisu, i punkt (c) — bo test, w którym cała baza jest
tylko-do-odczytu, przeszedłby (a) i (b) nie mając ani jednego wyzwalacza.

## AC-3 Każde połączenie dostaje ten sam komplet pragm
check: cargo test --test store_pragmas

Dla **każdego** publicznego konstruktora, jaki moduł wystawia (`Store::open(path)` i jego połączenie
pisarza, `Store::reader()`), zapytaj o pragmy i sprawdź: `busy_timeout` = 5000, `foreign_keys` = 1,
`synchronous` = 1 (NORMAL), a na bazie plikowej `journal_mode` = `wal`. Uwaga, o którą się tu
potyka: `journal_mode` jest własnością **bazy** i trwa w pliku, a `busy_timeout`, `foreign_keys` i
`synchronous` są własnością **połączenia** i wracają do wartości domyślnych przy każdym nowym —
`foreign_keys` domyślnie jest **wyłączone**, więc czytelnik, który go nie ustawi, po cichu nie widzi
kaskad. Kontrola przeciw pustej asercji: gołe `Connection::open(path)` otwarte w teście raportuje
`busy_timeout` = 0 i `foreign_keys` = 0 — jeśli ta kontrola nie jest czerwona, asercja nic nie mierzy.

*Słaba asercja:* sprawdzenie pragm tylko na połączeniu zwróconym przez `open()`. Przechodzi, gdy
`reader()` omija helper i idzie prosto do `Connection::open_with_flags` — czyli w dokładnie tym
przypadku, który zabolał w produkcji. Dyskryminuje: pętla po **wszystkich** publicznych
konstruktorach plus kontrola na gołym połączeniu. Czego to sprawdzenie **nie** widzi i trzeba to
wiedzieć: konstruktora dodanego jutro, który znowu ominie helper — to zostaje ludzkim osądem i
recenzją, i tak ma zostać.

## AC-4 Skasuj bazę, odbuduj z plików, dostań te same wiersze
check: cargo test --test store_disposable

Niezmiennik 4, i to jest jedyne kryterium, które trzyma ten podsystem przy życiu. Zbuduj na dysku
prawdziwy katalog biegu (`run.json` z dwoma krokami, `logs/agent-<id>.jsonl` z kilkunastoma
zdarzeniami, `handoffs/01__…md`), zaindeksuj go, po czym zrzuć **wszystkie wiersze wszystkich
tabel** — kolumny wyliczaj z `PRAGMA table_info(<tabela>)`, nie z listy wpisanej w test. Skasuj plik
bazy. Wywołaj `Store::rebuild_from(run_dir)`. Zrzuć ponownie. Asercja: zrzuty są równe, wraz z
`events` w tej samej kolejności `seq`, `steps.cost_usd`, `steps.summary`, `steps.agent_session_id`
i `runs.workflow_snapshot`.

*Słaba asercja:* porównanie `SELECT count(*)` po każdej tabeli albo porównanie samej tabeli `runs`.
Przechodzi, kiedy odbudowa gubi `cost_usd` i `summary` — czyli dokładnie te dwa pola, które nikt nie
pomyślał zapisać do `run.json`. Dyskryminuje: wyliczanie listy kolumn z `PRAGMA table_info` zamiast
wpisywania jej ręcznie — dzięki temu **kolumna dodana jutro** automatycznie wchodzi do porównania i
nie da się jej po cichu wyjąć spod niezmiennika.

## AC-5 Jeden pisarz wytrzymuje ośmiu producentów i nikt nie gubi wiersza
check: cargo test --test store_single_writer

Osiem zadań tokio wysyła po 500 zdarzeń kanałem pisarza, każde z unikalnym `body`. Asercje: każde
wysłanie zwróciło `Ok`; po zamknięciu kanału i zaczekaniu na zadanie pisarza `SELECT count(*) FROM
events` = 4000; zbiór 4000 `body` jest kompletny (żaden nie zginął, żaden nie zdublował się); żaden
błąd po drodze nie zawiera `SQLITE_BUSY` ani `database is locked`. Druga połowa: publiczne API nie
daje żadnej drogi do drugiego połączenia zapisującego — `INSERT` na połączeniu z `Store::reader()`
kończy się błędem „attempt to write a readonly database".

*Słaba asercja:* jeden producent, 4000 wierszy, `count == 4000`. Przechodzi na implementacji bez
kanału i bez zadania pisarza, która po prostu zapisuje z bieżącego wątku — i wykłada się dopiero na
drugim agencie. Dyskryminuje: **osiem** równoległych producentów oraz porównanie **zbioru** treści,
nie licznika (licznik nie odróżnia „zgubiłem jeden i zdublowałem inny" od poprawnego biegu).

## AC-6 Wsad 100 wierszy to jedna transakcja, a zły wiersz nie zabija pisarza
check: cargo test --test store_batch_atomic

Wyślij wsad 100 zdarzeń, w którym 57. łamie `CHECK` (`level = 'loud'`, spoza
`headline|detail|raw`). Asercje: po tym wsadzie liczba wierszy w `events` jest **taka sama jak
przed** — żadnych 56 sierot; błąd wraca do wołającego i nazywa wsad; a **następny**, poprawny wsad
100 wierszy ląduje w całości, czyli zadanie pisarza przeżyło i nie trzeba restartować aplikacji.

*Słaba asercja:* `assert!(result.is_err())`. Przechodzi na implementacji, która wstawia wiersze
1–56, przewraca się na 57. i zostawia bazę w połowie — a to jest gorsze niż brak wsadu, bo transkrypt
ma dziurę, o której nikt nie wie. Dyskryminuje: równość licznika **sprzed** i **po** feralnym wsadzie
oraz udany wsad następny (bez tego drugiego przechodzi implementacja, która ratuje atomowość,
zabijając pisarza).

## AC-7 Schemat odmawia sam, bez pomocy Rusta
check: cargo test --test store_strict_schema

Na połączeniu otwartym **bezpośrednio** w teście: (a) `INSERT INTO steps(status,…) VALUES('finished',…)`
→ `Err` z `CHECK` (siedem dozwolonych stanów z ARCHITECTURE §5: `pending`, `ready`, `running`,
`succeeded`, `failed`, `cancelled`, `skipped`); (b) `INSERT INTO steps(attempt,…) VALUES('dwa',…)`
→ `Err`, bo tabela jest `STRICT` (bez `STRICT` SQLite to przyjmie i policzy jako tekst);
(c) `DELETE FROM runs WHERE id=?` kasuje kaskadą jego `steps` i `events` — przy `foreign_keys` ON,
z AC-3; (d) `INSERT` dwóch kroków z tym samym `(run_id, node_key)` → `Err` z `UNIQUE`.

*Słaba asercja:* sprawdzenie, że nasza funkcja `insert_step` odrzuca zły status. Przechodzi na
schemacie bez jednego `CHECK` i bez `STRICT` — a wtedy pierwszy zapis spoza naszego API (migracja,
odbudowa z AC-4, skrypt) wpuszcza stan, którego UI nie umie narysować, i widok pokazuje pustkę.
Dyskryminuje: wszystkie cztery próby idą **surowym SQL-em na surowym połączeniu**, więc czerwień
może pochodzić wyłącznie od schematu.

## Świadomie poza zakresem

- **Pełne czytanie dla UI** (zapytania szyny, historii, wyszukiwanie po `events`): tutaj powstaje
  tylko tyle odczytu, ile potrzebują kryteria. Widoki dokłada T-08 przez `ipc.rs` (T-07).
- **`memory` jako funkcja.** Tabela z T7 §5.4 wchodzi do schematu teraz (dodawanie tabel później też
  jest addytywne, ale schemat lubi być kompletny raz), a sekcja Pamięć, promocja notatek i FTS5 to
  T-16 i T-17.
- **Sprzątanie po awarii.** `UPDATE runs SET status='interrupted'` na starcie, reap po `pgid` i
  zabezpieczenie czasem startu maszyny to T-20; tutaj powstaje tylko schemat, który to umożliwia
  (`steps.pid`, `steps.pgid`).
- **Kompaktowanie i pruning `events`.** 200 000 zdarzeń odtwarza się w 22 ms [T7 §5.3] — wracamy do
  tematu przy 10 mln.
- **Druga wersja schematu.** Jedna wersja, aż zajdzie potrzeba drugiej (AGENTS.md, tabela zakazów).
  Nie ma tabeli wersji i nie ma frameworka migracji poza `rusqlite_migration`.
- **Wydajność ponad zmierzone minimum.** Liczby z T7 §5.3 są kilka rzędów wielkości ponad potrzebą;
  nie ma tu kryterium na przepustowość i nie ma go celowo — byłoby to kryterium, które mierzy maszynę.
