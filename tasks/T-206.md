# T-206 — Deterministyczna odmowa triggera czeka na zmianę albo Retry

Wadliwy workflow triggera jest dziś ponawiany przy każdym ticku. Trwały ledger zna Pending i
Accepted, lecz pełny planner biegnie dopiero po związaniu dostawy przez Start. Jeden błąd
konfiguracji mnoży więc próby i log, a zmiana closure między Poll i Start może ominąć wcześniejszą
walidację. Dodatkowo task dla issue składa dziś JavaScript, choć trwały claim i planner należą do
Rusta.

Zadanie dodaje typed durable quarantine, ale nie drugą maszynę stanów ani frontendowy ledger.
Manualny Run, Poll i triggerowy Start używają jednego read-only preflightu z `AppState`/`RunDeps`.
Rust składa i przechowuje kanoniczne zadanie, a UI wyłącznie pokazuje typowany stan i wysyła
adresowany Retry. Minimalna migracja ledgera zachowuje aktywne payloady oraz co najwyżej jeden
najnowszy seed do jawnego Run again; nie tworzy bezterminowej historii payloadów.

**Zależy od:** T-155, T-158 i T-205. T-155 dostarcza adresowany rejestr biegów, T-158 prywatne
descriptor-relative podnoszenie plików legacy, a T-205 wspólną politykę sekretów potrzebną do
bezpiecznego fingerprintu pełnej closure.

- Obowiązują uczciwe czerwone `before`, quick/full, jedna recenzja, najwyżej jedna naprawa i jedno

- Fixture używa wyłącznie tymczasowej biblioteki, repo i fikcyjnych markerów. Nie zmieniaj

  Ciężkie Cargo biegnie pojedynczo na całej maszynie.

## Jeden kontrakt preflightu

Wspólny read-only preflight zwraca typowany wynik `Ready` albo `Refused` z klasyfikacją:

- `QuarantineEligible` — deterministyczna odmowa zależna wyłącznie od zamrożonego taska i pełnej
  lokalnej closure, której zmianę da się wykryć fingerprintem;
- `Transient` — stan, który może zmienić się bez zmiany closure, na przykład chwilowa odmowa
  odczytu; nie staje się trwałą kwarantanną;
- `UnsafeUnknown` — nowy albo niejednoznaczny błąd. Odmawia fail-closed, ale nigdy nie jest
  zgadywany jako deterministyczny na podstawie tekstu.

Klasyfikacja mieszka przy jednym typie błędu planowania, nie w dwóch adapterach ani w UI. Funkcja
ładuje dokładnie te workflowy, agentów, skills i Connections, których użyje `plan_run`, ale nie
rezerwuje biegu, nie zakłada worktree, nie konsumuje limitera, nie zapisuje ledgera i nie startuje
drivera. Manualny Run wyświetla tę samą odmowę; tylko triggerowy caller ma prawo atomowo zapisać
`Quarantined` dla `QuarantineEligible`.

Kanoniczny task powstaje w Ruście z identyfikatora, tytułu i body issue dokładnie raz, z jedną
udokumentowaną normalizacją. Jest zapisany przy dostawie i użyty przez oba preflighty oraz plan.
Frontend nie ma `taskForIssue` ani drugiej składni. Jeśli istniejąca krawędź Start nadal przesyła
task razem z claimem, backend porównuje go bajtowo z autorytetem ledgera i planuje wyłącznie
wartość rustową; brak lub różnica są odmową przed rezerwacją.

## Uczciwe `before`

Oba rustowe targety istnieją, kompilują się i przechodzą przez produkcyjny `AppState`, ledger oraz
prawdziwy planner; frontendowy target montuje ekran Triggers z produkcyjnym store/IO. Przed zmianą
AC-1 pada na ponownej walidacji, braku trwałego stanu albo starcie po kontrolowanej zmianie między
Poll i Start. AC-2 pada na widocznym statusie, adresie Retry albo tasku złożonym przez JavaScript.
AC-3 pada na retained terminalnym payloadzie, starym schemacie albo zbyt szerokich prawach.

Brak symbolu/targetu, compile lub collection error, timeout przez `sleep`, zero testów, test
samego helpera, klasyfikacja tekstu albo ręcznie podany prop, którego produkcyjny caller nie ma,
nie są prawidłową czerwienią.

## AC-1 Kwarantanna przeżywa restart i używa preflightu Run także przy Starcie
check: cargo test --test t206_trigger_quarantine_uses_shared_preflight
expect: (\d+) passed

Target pyta produkcyjne `check_trigger`, a potem wchodzi przez ten sam triggerowy Start co okno,
z realnym `AppState`/`RunDeps` i liczącym fake-driverem. Fixture zawiera osobne błędy wykrywalne
dopiero w referenced agencie, skillu i Connection. Każdy `QuarantineEligible` odmawia przed
`Pending` albo — w scenie wyścigu opisanej niżej — atomowo zamienia istniejący `Pending` na
`Quarantined`. Nie powstaje rezerwacja biegu, worktree ani start drivera.

Kontrolowany hook daje najpierw zielony Poll, zapisujący Pending, a potem zmienia element closure
przed wejściem Startu. Start ponawia ten sam read-only preflight bezpośrednio przed `Bound`.
Deterministyczna odmowa zapisuje dla tej samej dostawy `Quarantined { deliveryId, generation,
fingerprint, sentence }`; nie zostawia równocześnie Pending i nie publikuje `run.json`. Po
restarcie następne dziesięć ticków nie waliduje ani nie uruchamia niezmienionej closure drugi raz.
`Transient` i `UnsafeUnknown` są osobnymi typed wynikami, odmawiają bez startu i nigdy nie są
utrwalane pod nazwą `Quarantined`.

Causal fingerprint jest kryptograficznym hashem stabilnej, sortowanej i length-framed listy
komponentów. Obejmuje:

- kanoniczny task oraz dokładne bajty workflowu, wszystkich rozwiązanych agentów i użytych
  `SKILL.md`/plików skilla, wraz z bezpieczną tożsamością każdego komponentu;
- kanoniczną, zredagowaną projekcję każdej użytej Connection: wszystkie pola niesekretne, nazwy
  referencji env i bit obecności rozwiązanej wartości;
- wersję schematu fingerprintu, schematu definicji oraz bieżącą wersję aplikacji.

Nie obejmuje wartości rozwiązanego env, klucza triggera ani żadnego innego sekretu — także w
postaci osobnego hash-a umożliwiającego zgadywanie offline. Zmiana taska albo dowolnego komponentu
closure wykonuje dokładnie jedną nową walidację i zdejmuje starą kwarantannę. Jawny Retry z
właściwymi `slug`, `deliveryId` i generacją robi to samo bez zmiany plików; stale lub powtórzony
Retry jest typed odmową i nie tworzy drugiej próby. Partial `JSON.stringify(Choice)`, zestaw nazw
plików i tekst błędu nie są oracle fingerprintu.

## AC-2 Człowiek widzi kwarantannę i uruchamia rustowy task jednym Retry
check: npx --no-install vitest run src/sections/triggers/t206-refusal-is-quarantined.test.tsx
expect: (\d+) passed

Prawdziwy ekran Triggers dostaje typed `TriggerPoll::Quarantined` przez produkcyjne IO/store,
pokazuje przy właściwym wierszu bezpieczne angielskie zdanie i nie woła `launchRun` dla tej
dostawy. Działający przycisk Retry wysyła dokładnie raz `slug`, `deliveryId` i bieżącą generację
otrzymaną z Rusta; nie klasyfikuje tekstu, nie liczy własnej generacji i nie tworzy drugiego
ledgera w przeglądarce. Odpowiedź stale-generation pozostawia aktualną kwarantannę widoczną.

Zdrowa dostawa przechodzi przez produkcyjny watcher i Start, ale task użyty przez Run pochodzi z
ledgeru Rusta. Target daje JS-owi issue, przy którym dawne `taskForIssue` zbudowałoby inną wartość,
i dowodzi exact tasku przyjętego przez backend. Nie montuje samego `Row`, nie podaje prywatnego
propsa i nie powtarza scenariusza pełnej puli ani wielu workspace'ów z T-155.

## AC-3 Ledger kompaktuje payload i zachowuje prywatną granicę
check: cargo test --test t206_trigger_terminal_payloads_are_compact
expect: (\d+) passed

Nowy zapis ma schemat 2. Loader czyta prawidłowy schema 1 bez utraty Pending/Bound/Accepted i
normalizuje go w pamięci; dopiero następna rzeczywista mutacja publikuje cały ledger jako schema 2.
Nie powstaje migracja SQLite ani zapis tylko po to, żeby podbić numer.

Schema 2 zachowuje pełny payload wyłącznie dla aktywnego Pending, Bound lub Quarantined oraz co
najwyżej jeden najnowszy Accepted `retrySeed`, zawierający minimum potrzebne do jawnego Run again
i odtworzenia kanonicznego taska. Kolejny Accepted zastępuje poprzedni seed. Starsze Accepted i
Cancelled znikają z listy dostaw po złożeniu najnowszego zredagowanego receipt-u i dowodu
exactly-once; nie zachowują issue body, taska ani powtarzalnej closure. Setki cykli oraz Retry tej
samej sprawy nie zwiększają liczby ciężkich rekordów.

`seen_ids` nadal rośnie dokładnie raz na nowy zewnętrzny identyfikator, bo jest trwałym dowodem
exactly-once; nie rośnie od ticków ani Retry tej samej dostawy. To jawny, lekki zbiór tożsamości,
nie ukryta kopia payloadu. Restart po trwałych granicach publikacji zachowuje aktywną próbę,
najnowszy retry seed, ostatni zredagowany receipt oraz crash-window T-65.

Pliki konfiguracji triggera i ledgera są regularnymi plikami bieżącego efektywnego użytkownika,
otwieranymi no-follow i utrzymywanymi jako dokładnie `0600`. Bezpieczny legacy regular file tego
samego właściciela z szerszym trybem jest zacieśniany przez otwarty deskryptor przed odczytem lub
zapisem. Symlink, katalog i plik innego właściciela są fail-closed i pozostają nietknięte.
Publikacja/recovery korzysta z granicy T-210/T-158, nie z path-based `metadata → write`.

Fikcyjne wartości secret env i klucza triggera nie występują w ledgerze, fingerprintcie, typed
IPC, `Debug` ani odmowie, również po schema 1 → 2. Connection fingerprint zapisuje wyłącznie
zredagowaną projekcję opisaną w AC-1.

## Jawnie poza zakresem

- Powrót statycznego rejestru locków do dokładnego baseline'u po setkach historycznych slugów nie
  jest kontraktem tego zadania. Nie wolno dopisywać cleanupu mapy wyłącznie pod taki oracle.
- Globalny limiter, Waiting i niezależność workspace'ów należą do T-155 i nie są tu drugi raz
  testowane.
- Nie ma wyczerpującej macierzy restartu po każdym wewnętrznym fault poincie; testowane są trwałe
  granice publikacji ledgera oraz istniejące oracles T-65.
- Nie powstaje kolejka retry, backoff daemon, zewnętrzna telemetria, frontendowa polityka błędów
  ani automatyczne kasowanie raw evidence, handoffów, rozmów Lead lub historii użytkownika.
