# T-39 — Ekran Run wyglada jak makieta i zaprasza do dzialania

Powloka zgadza sie z makieta od T-37: menu 196 px z boku, marka, piec sekcji, stopka. **Wnetrze
ekranu Run nie zgadza sie z niczym.** Zmierzone 2026-08-18 w przegladarce, na wyladowanym trunku:

```
document.body.innerText  ->  LOADOUT · Run · Workflows · Agents · Skills · Memory
                             Claude · Codex ready · Run · No workflows saved yet
                             Start · How many agents at once? · 3
                             ◇ Nothing here yet: the work shows up line by line.
main button              ->  ["Start [disabled]"]
```

**W swiezej aplikacji ekran Run ma dokladnie jeden przycisk i jest on wylaczony.** Czyli nie
zaprasza do niczego, a `docs/design/DESIGN.md` §6 mowi wprost: „Pusty ekran to zaproszenie do
dzialania, nie komunikat o braku danych." To nie jest usterka kosmetyczna — to jedyny ekran,
od ktorego zaczyna sie praca w tym produkcie.

Makieta (`docs/mockup/index.html`, `data-screen="work"`) opisuje go jednoznacznie:

```css
.work    { display:grid; grid-template-columns: minmax(0,1fr) 268px; min-height:0 }
.feedcol { display:grid; grid-template-rows: minmax(0,1fr) auto auto; min-height:0 }
.tabs    { height:34px }
.strip   { height:56px }
.rail    { grid-template-rows:auto minmax(0,1fr); border-left:1px solid var(--line) }
```

Czyli trzy rzedy (karty, pasek loadoutu, praca), a praca to dwie kolumny: kolumna strumienia
i **szyna agentow 268 px**. Dzis nie ma ani kart, ani szyny, ani wiersza wejscia.

**Zadne z tego nie jest do napisania od zera, i to jest sedno tego zadania.** Wszystkie cztery
mechanizmy wyladowaly i stoja bez miejsca montowania — ta sama rodzina, ktora wymusila T-26
i T-27:

| co | co juz jest | czego brakuje |
|---|---|---|
| szyna agentow | `rail/roster.ts`, `rail/card.ts`, `rail/colour.ts`, `rail/say.ts` — komplet logiki | komponentu `.tsx` **nie ma w ogole** |
| karty workspace | `tabs/tab-bar.tsx`, `tabs/tab.tsx`, `tabs/picker.tsx` | nikt ich nie montuje |
| pauza dostawcy | `limits/paused-banner.tsx` | nikt go nie montuje |
| wiersz wejscia | — | nie istnieje |

`checks/quick-wired.sh` tego nie widzi, bo pilnuje `pub fn` w Ruscie. Po stronie frontu jedyna
wyrocznia na „zamontowane, a nie tylko istnieje" to e2e z T-29 — i ona **juz to zglosila**:
`no-dead-controls.spec.ts` niesie wpis w `EXCUSED` dla `Start`, ktorego powod konczy sie zdaniem
„ten wpis znika, kiedy T-39 dowiezie te bloki". AC-6 kasuje ten wpis.

**Read first:**
`docs/mockup/index.html` — sekcja `data-screen="work"` oraz reguly `.work`, `.feedcol`, `.tabs`,
`.strip`, `.rail`, `.card`, `.entry`, `.box` · `docs/ARCHITECTURE.md` §7 (sufit gestosci, cztery
linie na kafelek agenta, dwie osie nawigacji) · `docs/design/DESIGN.md` §3 („Tozsamosc ≠ stan"),
§6 (`agent-card`, `empty-state`) · `src/sections/run/rail/card.ts` (`RailCard` — szesc pol)
· `src/ui/shell/shell-matches-mockup.test.tsx` (wzorzec czytania makiety jako wyroczni).

## Zalezy od

**T-38.** Szyna, karty i wiersz wejscia pokazuja stan biegu, a bieg zaczyna dochodzic do okna
dopiero z T-38 (Start zaklada kanal, linie wchodza do magazynu). Zbudowane wczesniej, wszystkie
cztery bloki mialyby na wejsciu wylacznie pusty magazyn — czyli nie dalyby sie odroznic od
ozdoby (niezmiennik 17).

## Co to zadanie posiada

- `src/sections/run/index.tsx` — **waski mandat**: uklad trzech rzedow z makiety plus miejsca
  montowania czterech blokow. Nie zmienia sie ani `Feed`, ani `Now`, ani `Strip`.
- `src/sections/run/rail/rail.tsx` — **nowy** komponent szyny. Bierze gotowe `RailCard`
  i **nie podejmuje ani jednej decyzji o tresci**: nie wybiera zdania, nie liczy stanu, nie
  przypisuje koloru. Gdyby podejmowal, polityka „kto to powiedzial" istnialaby dwa razy
  (niezmiennik 23).
- `src/sections/run/entry/entry.tsx` — **nowy** wiersz wejscia.
- Szesc plikow testow wymienionych przy `check:`.

**Czego to zadanie NIE dotyka:** wnetrza `Feed`, `Now`, `Strip` i `tabs/*` — te komponenty
istnieja i sa sprawdzone; brakuje im wylacznie miejsca montowania, a to jest zapis w `index.tsx`.
Ani jednego pliku w `src-tauri/**`.

## Niezmienniki

- **13 — jeden fakt, jedno miejsce.** Wymiary czytasz z makiety w tym samym biegu testu.
  `268` wpisane z palca przechodzi takze wtedy, gdy makieta mowi co innego.
- **16 — kontrolka bez handlera nie wchodzi do repo.** Wiersz wejscia bez dzialania jest
  gorszy niz jego brak: obiecuje sposob pracy, ktorego nie ma.
- **17 — UI nie rysuje relacji, ktorych nie ma w danych.** Szyna z pustym magazynem pokazuje
  **nic**, nie atrape agenta.
- **DESIGN §3 — tozsamosc ≠ stan.** Kwadrat agenta nosi kolor tozsamosci nawet wtedy, gdy agent
  jest `failed`. Stan jest SLOWEM w kolorze nasyconym. Ta regula powstala, bo referencyjny
  poprzedni prototyp dawal Forge'owi ten sam hex, co „wymaga uwagi".
- **ARCHITECTURE §7 — cztery linie tekstu na kafelek.** Piata linia to blad projektowy.

## Kryteria akceptacji

## AC-1 Uklad ekranu Run jest ukladem z makiety, czytanym z niej
check: npx --no-install vitest run src/sections/run/run-matches-mockup.test.tsx
expect: (\d+) passed

Test czyta z `docs/mockup/index.html` reguly `.work` i `.feedcol` i sadzi nimi wyrenderowany
ekran Run.

Asercje: (a) obszar pracy deklaruje dwie kolumny, a druga ma szerokosc **przeczytana z makiety**
(dzis 268 px); (b) kolumna strumienia deklaruje trzy rzedy w kolejnosci z makiety; (c) obie
wartosci zostaly z makiety naprawde odczytane — niepuste i o spodziewanej liczbie czlonow —
bo parser, ktory cicho zwrocil pustke, zamienilby (a) i (b) w porownanie dwoch pustych napisow.

*Slaba wersja:* `expect(markup).toContain('268px')`. Przechodzi, gdy `268px` stoi gdziekolwiek,
i przechodzi, gdy makieta zmieni sie na 300, a ekran nie.

## AC-2 Szyna agentow jest zamontowana i pokazuje to, co oddal `roster()`
check: npx --no-install vitest run src/sections/run/rail-shows-agents.test.tsx
expect: (\d+) passed

Asercje: (a) przy pustym magazynie szyna **nie renderuje ani jednego kafelka** — zero atrap
(niezmiennik 17); (b) dla stanu z dwoma agentami markup niesie dokladnie dwa kafelki, z nazwami
i zdaniami **z `roster()`**, a nie wpisanymi w test; (c) kolor kwadratu to token tozsamosci
tego agenta, a slowo stanu ma kolor stanu — sprawdzone na agencie `failed`, czyli tam, gdzie
pomylka jest najlatwiejsza; (d) kafelek niesie **cztery** linie tekstu, nie piec.

*Slaba wersja:* zaimportowanie `Rail` w tescie i wyrenderowanie go wprost. Przechodzi dzis,
bo komponentu nie ma, a jak powstanie — przejdzie takze wtedy, gdy nikt go nie zamontuje.
Rozstrzyga renderowanie CALEGO ekranu Run i szukanie szyny w jego markupie.

## AC-3 Karty workspace sa zamontowane i przelaczaja folder
check: npx --no-install vitest run src/sections/run/tabs-switch-workspaces.test.tsx
expect: (\d+) passed

Asercje: (a) ekran Run niesie pasek kart z `tabs/tab-bar.tsx`, a nie wlasna kopie; (b) klikniecie
karty zmienia otwarty workspace w magazynie; (c) karty odpowiadaja na pytanie „w ktorym
folderze", a menu boczne na „co robie" — czyli obie osie sa prostopadle i jest ich **dwie**
(ARCHITECTURE §7); (d) wysokosc paska to `34px` z makiety, przeczytane z niej.

*Slaba wersja:* `expect(markup).toContain('TabBar')`. Nazwa komponentu w markupie nie wystepuje,
a obecnosc pliku nie znaczy montazu.

## AC-4 Wiersz wejscia istnieje i jego kontrolka cos robi
check: npx --no-install vitest run src/sections/run/entry-row.test.tsx
expect: (\d+) passed

Asercje: (a) ekran Run niesie wiersz wejscia z zachetа i podpowiedzia z makiety; (b) kontrolka
ma handler, ktory cos zmienia — pusty `onSubmit` jest martwa kontrolka (niezmiennik 16);
(c) tekst zachety przechodzi tabele z DESIGN §8 — zaden zargon.

*Slaba wersja:* sprawdzenie samego `<input>`. Pole bez handlera obiecuje sposob pracy, ktorego
nie ma, i jest gorsze niz jego brak.

## AC-5 Pasek pauzy pokazuje sie wtedy i tylko wtedy, gdy bieg jest wstrzymany
check: npx --no-install vitest run src/sections/run/paused-banner-mounts.test.tsx
expect: (\d+) passed

Asercje: (a) przy biegu bez pauzy paska **nie ma** w markupie; (b) przy pauzie dostawcy jest,
i niesie moment wznowienia; (c) pochodzi z `limits/paused-banner.tsx`, a nie z drugiej kopii
tego samego zdania (niezmiennik 13).

*Slaba wersja:* wyrenderowanie `PausedBanner` wprost. To samo pytanie co przy AC-2: „istnieje"
to nie „zamontowany".

## AC-6 Pusty ekran Run zaprasza do dzialania, a `EXCUSED` wraca do pustej listy
check: npx --no-install vitest run src/sections/run/empty-invites.test.tsx
expect: (\d+) passed

Asercje: (a) na swiezym ekranie Run istnieje **co najmniej jedna czynna** kontrolka — dzis jest
zero, bo jedyny przycisk jest `disabled`; (b) `e2e/tests/no-dead-controls.spec.ts` nie niesie juz
wpisu `EXCUSED` dla `Start` — czytane z tego pliku, nie zalozone; (c) zdanie pustego ekranu jest
zaproszeniem, nie komunikatem o braku danych (DESIGN §6).

*Slaba wersja:* policzenie przyciskow. Przycisk `disabled` jest widoczny i policzalny, a nie
da sie go uzyc — dlatego punkt (a) pyta o kontrolke **czynna**.

## AC-7 Zamkniecie karty z zywym biegiem PYTA, a potwierdzenie naprawde zatrzymuje
check: npx --no-install vitest run src/sections/run/closing-a-tab-asks-and-stops.test.tsx
expect: (\d+) passed

*Dopisane 2026-08-18 po znalezisku sprawdzajacego — zadne z szesciu pierwszych kryteriow tego
nie dotykalo, a jest to jednoczesnie martwa kontrolka i blad finansowy.*

`WorkspaceTab.agents` bylo pisane WYLACZNIE przy zakladaniu karty i zawsze zerem. `requestClose`
decyduje na tym polu, wiec zawsze wchodzil w galaz „nic tu nie chodzi": karta z zywym biegiem
znikala bez pytania i bez `cancel(id)`. Bieg zostawal osierocony i dalej palil limit u dostawcy
— `src/state/workspaces.ts` nazywa to slowami niezmiennika 6: **blad finansowy, nie higieniczny**.
`CloseConfirm`, zamontowany i otestowany, byl przez to kodem NIEOSIAGALNYM.

Asercje: (a) karta, w ktorej nikt nie pracuje, zamyka sie BEZ pytania — potwierdzenie przy kazdym
zamknieciu uczy klikac „tak" bez czytania; (b) karta z agentami przy pracy PYTA i zostaje na
ekranie; (c) potwierdzenie wola anulowanie biegu i dopiero potem zdejmuje karte; (d) EKRAN
naprawde karmi ten licznik, i to ta sama lista, ktora rysuje szyne agentow (niezmiennik 13).

*Slaba wersja:* wywolanie `setAgents` wprost z testu i sprawdzenie, ze pole uroslo. Przechodzi
na kodzie, w ktorym EKRAN nigdy tego settera nie wola — czyli na dokladnie tym defekcie.
Punkt (d) czyta zrodlo ekranu, bo render serwerowy nie uruchamia efektow; ta polowa jest
slabsza i jest w nagl3owku testu NAZWANA, a nie przemilczana.
