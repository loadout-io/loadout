# T-154 — Rerun odtwarza wyłącznie zadeklarowane wejście kroku

Dzisiejszy rerun kopiuje całe katalogi `handoffs/` i `attachments/`, a potem rekonstruuje
kontekst z tego, co akurat jeszcze leży obok starego biegu. To jest szersza capability niż
receipt i nie daje odpowiedzi, czy powtórzony krok dostał te same plikowe wejścia. Ten task
rozszerza istniejący per-step manifest o addytywne `stagedFiles`: zamkniętą listę handoffów
i attachments, które Loadout przekazał temu fizycznemu krokowi, z bezpieczną ścieżką względną,
liczbą bajtów i SHA-256 dokładnych bajtów.

Manifest nie jest sandboxem OS. Agent nadal może czytać swój katalog roboczy zgodnie z
uprawnieniami vendora. Kontrakt mówi wyłącznie, które materiały Loadout deklaruje, kopiuje do
prywatnego stagingu kroku, wymienia w prompcie i jawnie przekazuje jako dodatkowy kontekst.

**Zależy od:** T-151, T-153, T-155, T-156 i T-210, który ląduje wspólny stos T-202/T-210.

**Read first:** `AGENTS.md` niezmienniki 4, 5, 9, 19, 21, 23 i 24 · `tasks/T-88.md` ·
`tasks/T-133.md` · `src-tauri/src/evidence.rs` (`SafeInputManifest`, `ContextSource`) ·

## Tryb wykonania — DIRECT / medium

1. Codex tworzy osobny worktree przez `./worktree.sh T-154`; nie używa `ship-task.sh`,
   `review.sh` ani `repair.sh`.
2. Najpierw dodaje oba kompletne targety i najwęższe kompilowalne szkielety produkcyjnych typów.
   Każdy `check:` uruchamia osobno i zapisuje czerwień na asercji starego zachowania: rerun
   wystartował mimo brakującego pliku albo staging zawiera sentinel spoza manifestu. Brak modułu,
   compile error, zero testów i timeout nie są dowodem.
3. Implementuje wyłącznie `OWNS`, uruchamia oba targety i `./verify.sh quick`; osobny Codex robi
   lekki read-only review diffu bez `review.sh`. Jedynym lądowaniem jest pojedyncze
   `./integrate.sh <gałąź>`, które wykonuje pełną bramkę.
4. Nie zmienia Harnessu, `checks/`, `verify.sh`, workflowów operatora ani lokalnych receiptów.

## Kontrakt manifestu wejścia

Istniejący `SafeInputManifest.context` zachowuje wire shape i znaczenie. Addytywne pole
`stagedFiles` opisuje wyłącznie dwa zamknięte rodzaje plikowego wejścia: `Handoff` i `Attachment`.
Jedna pozycja zawiera bezpieczną ścieżkę względną w kontrolowanym katalogu źródłowym, liczbę
bajtów oraz SHA-256 tych bajtów. Implementacja używa jednej bezpośredniej biblioteki SHA-256;
nie zastępuje kryptograficznego hasha istniejącym, niekryptograficznym fingerprintem. Ścieżka
absolutna, `..`, symlink i plik spoza kontrolowanego korzenia są odmową. Puste `stagedFiles` jest
legalnym faktem „ten krok nie miał takiego plikowego wejścia”; brak tego pola w starym manifeście
oznacza nieznany closure, nie pustą listę. Stare receipts pozostają czytelne, lecz `again`/`onward`
odmawiają dokładnego rerunu zdaniem mówiącym, że wejścia nie zostały zapisane.

Manifest jest per **physical step UUID**, nie per nazwa kafelka ani logiczny step id: dwie kopie
i dwie rundy pętli mogą mieć inne wejścia. Frontendowe `again`/`onward` nadal wskazuje logiczny
kafelek. Po wyznaczeniu fizycznych headów nowego slice'a backend mapuje stabilny `node_key`
każdego headu na dokładnie jeden `StepEntry` starego `run.json`, bierze z niego stary physical
UUID i dopiero nim adresuje manifest. Brak, duplikat lub niejednoznaczność mapowania — także po
zmianie liczby kopii, rund albo kształtu rozwiniętego grafu — jest odmową przed driverem. Backend
nigdy nie wybiera pierwszego manifestu o pasującej nazwie kafelka.

Każda fizyczna próba, która dochodzi do granicy `AgentDriver::start`, ma kompletny stage i manifest
opublikowany **przed** wywołaniem drivera; dotyczy to także `start -> Err`. Krok pominięty lub taki,
który nie doszedł do granicy startu, nie dostaje zmyślonego manifestu. Manifest powstaje z tego
samego zamrożonego zbioru bajtów, z którego Loadout buduje prompt i staging, a nie jako raport
dopisany po starcie.

Skills nie należą do `stagedFiles`. Task nie zamraża `SKILL.md`, nie dodaje skill hashy i nie
zmienia lifecycle materializacji skills. Definicja workflowu, agenta i istniejące bezpieczne
pozycje `context` zachowują dotychczasową semantykę.

## AC-1 Rerun wymaga całego zadeklarowanego wejścia fizycznego kroku
check: cargo test --test t154_rerun_replays_declared_step_inputs
expect: (\d+) passed

Produkcyjny bieg zapisuje dla dwóch fizycznych kroków różne `stagedFiles` zawierające handoffy
i powiązane attachments. `again` wybiera manifest dokładnego starego physical step UUID;
`onward` wybiera deklarowane wejście każdego fizycznego headu punktu wznowienia i nie zasiewa
materiałów, których ten head nie otrzymał. Zdrowa scena odtwarza wszystkie bajty i startuje
fake-driver dokładnie raz.

Osobna scena rozwija ten sam logiczny kafelek do kopii i rund o różnych `node_key`, UUID oraz
manifestach. Każdy head dostaje własne wejście dokładnie raz. Brakujące albo zduplikowane
mapowanie oraz zmiana liczby kopii lub rund odmawia przed pierwszym driverem zamiast arbitralnie
wybrać cudzy physical UUID.

Osobne sceny po zakończeniu starego biegu usuwają zadeklarowany plik, zmieniają jego bajty przy
tej samej długości, podmieniają rozmiar, podstawiają symlink i odbierają odczyt kontrolowanego
katalogu. Każda odmawia przed driverem, nazywa bezpieczną względną ścieżkę i nie interpretuje
braku jako pustego katalogu. Nieuszkodzony plik leżący obok, lecz niewymieniony w manifeście,
nie jest wymagany ani kopiowany. Stary zdrowy kontrakt T-88 nadal przechodzi.

Uszkodzony `run.json` nie jest sceną tego AC: rerun potrzebuje go do znalezienia workflowu i
kroku niezależnie od kontekstu, więc jego odmowa nie dowodzi closure manifestu.

## AC-2 Staging, prompt i jawna capability mają dokładnie ten sam zbiór
check: cargo test --test t154_step_input_stage_matches_manifest
expect: (\d+) passed

Obok dozwolonych plików A i attachment A leżą sentinele B. Produkcyjna droga Start buduje stage
fizycznego kroku w prywatnym katalogu i umieszcza w nim wyłącznie A oraz attachment A. Manifest
opisujący dokładnie ich ścieżki, bajty i hashe jest publikowany istniejącym durable publisherem
**jako ostatni element i commit marker stage'a**. Loader oraz driver uznają stage za widoczny
wyłącznie przy obecnym, czytelnym i zgodnym manifeście; nie powstaje drugi mechanizm atomowej
podmiany całego katalogu.

Fake-driver odbiera prawdziwy `RunSpec`. Prompt wskazuje wyłącznie ścieżki ze stage'a, a jawnie
przekazane katalogi nie obejmują wspólnych `handoffs/`, `attachments/` ani katalogu innego kroku.
Oracle enumeruje tylko powierzchnię kontekstu deklarowaną przez Loadout: `RunSpec.extra_dirs`
oraz staged paths wymienione w prompcie. Znajduje A i nie znajduje B na tej powierzchni. Nie jest
to obietnica sandboxa OS ani odmowy dowolnego odczytu workspace'u przez narzędzia vendora;
Claude może dostać stage przez `extra_dirs`, a Codex przez ścieżki w stdin promptcie.

Kontrolowany fault przed publikacją manifestu nie uruchamia drivera i zostawia zero committed
stage'a; prywatne przygotowanie należy do transakcyjnego cleanupu T-152. Po publikacji manifestu
ponowny odczyt widzi wyłącznie pełny stage, staged bytes zgadzają się z SHA-256 i manifest nigdy
nie wskazuje brakującego pliku. Ponieważ stage ma unikalny physical UUID, test nie wymaga
„poprzedniej wersji” ani fault matrix katalogowego replace.
