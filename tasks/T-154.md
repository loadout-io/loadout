# T-154 — Receipt, prompt i capability opisują ten sam kontekst

Zdrowy bieg przekazuje tekstowe handoffy poprawnie. Brakujące przecięcia są groźniejsze:
rerun potrafi pominąć zadeklarowany plik, Claude dostaje szerszy katalog niż receipt, skills
są kopiowane w różnych chwilach. Zadanie nie przebudowuje formatu handoffu ani receiptów
pamięci z T-133. Tożsamość kontekstu wielu bieżących runów należy do T-155.

**Zależy od:** T-151, T-153 i T-156. T-156 najpierw ustala lifecycle prywatnego stanu obu
driverów, których ten task dotyka ponownie.

**Read first:** `AGENTS.md` niezmienniki 4, 5, 9, 19, 23 i 24 · `tasks/T-87.md`,
`tasks/T-88.md`, `tasks/T-133.md` · `src-tauri/src/commands/run.rs`
(`copy_the_files_in`, `index_of_what_came_before`, `handed_before`) ·
`src-tauri/src/commands/rerun.rs` · `src-tauri/src/memory/handoff.rs` ·
`src-tauri/src/skills/mod.rs`, `skills/place.rs` · oba sterowniki.

## Tryb wykonania

- **Agent:** Codex w osobnym worktree, bez `ship-task.sh`.
- **Druga opinia:** osobny Codex na innym modelu, read-only; właścicielski same-vendor D3.
- Wywołania: `./review.sh --agent codex --reviewer codex`, a jeśli są uwagi, dokładnie raz
  `./repair.sh --agent codex --reviewer codex`. Nie uruchamiaj domyślnego agenta Claude.
- Pełna ręczna pętla; zero zmian w Harnessie.

## Uczciwe `before`

Oba targety istnieją. Rerun pada na asercji, bo wystartował; capability pada na realnym
argv/materializacji. Brak fixture, collection error i test, który tylko czyta helper, nie są
czerwienią.

## AC-1 Rerun odmawia utraty zadeklarowanego kontekstu
check: cargo test --test t154_rerun_requires_declared_context
expect: (\d+) passed

Zakończony receipt deklaruje konkretne handoffy i attachments. Osobne sceny usuwają plik,
uszkadzają Markdown, uszkadzają `run.json` i odbierają możliwość odczytu katalogu. `again` oraz
`onward` odmawiają przed driverem, nazywają brakujący materiał i niczego nie interpretują jako
pusty katalog. Prawdziwy brak opcjonalnego katalogu pozostaje legalny. Stary zdrowy rerun z
T-88 nadal przechodzi.

## AC-2 Agent dostaje dokładnie to, co zapisuje manifest
check: cargo test --test t154_context_capability_matches_receipt
expect: (\d+) passed

Obok dozwolonego handoffu A leży niepowiązany sentinel B. Produkcyjna materializacja tworzy
per-step katalog kontekstu zawierający wyłącznie A i wybrane attachments. Prompt, manifest i
hashe wymieniają dokładnie ten sam zbiór. Pełne argv obu vendorów nie przyznaje wspólnych
`handoffs/` ani `attachments/`; atrapa enumeruje wszystkie katalogi kontekstu jawnie przekazane
przez Loadout i znajduje A, nie B.

To dowodzi wyłącznie granicy kontrolowanej przez Loadout: co staging i driver przekazują jako
kontekst kroku. Nie jest to obietnica sandboxa OS ani odmowy dowolnego odczytu workspace przez
narzędzia vendora; v1 takiego sandboxa świadomie nie ma, a UI/receipt nie może go sugerować.

Ten sam run zamraża bytes+hash każdego skilla raz. Hook zmienia `SKILL.md` po planowaniu, lecz
wszystkie kroki tego biegu dostają jedną wersję; następny bieg dostaje nową. Receipt zapisuje
hash, nie pełną prywatną treść.
