# T-154 — Rerun odtwarza wyłącznie zadeklarowane wejście kroku

Dzisiejszy rerun kopiuje całe katalogi `handoffs/` i `attachments/`, a potem rekonstruuje
kontekst z tego, co akurat jeszcze leży obok starego biegu. To jest szersza capability niż
receipt i nie daje odpowiedzi, czy powtórzony krok dostał te same plikowe wejścia. Ten task
wprowadza jeden per-step manifest będący zamknięciem wejścia: względna ścieżka, liczba bajtów
i hash dokładnych bajtów każdego pliku, który Loadout przekazał temu fizycznemu krokowi.

Manifest nie jest sandboxem OS. Agent nadal może czytać swój katalog roboczy zgodnie z
uprawnieniami vendora. Kontrakt mówi wyłącznie, które materiały Loadout deklaruje, kopiuje do
prywatnego stagingu kroku, wymienia w prompcie i jawnie przekazuje jako dodatkowy kontekst.

**Zależy od:** T-151, T-153, T-155, T-156 i T-202.

## Kontrakt manifestu wejścia

Każdy rzeczywiście uruchomiony fizyczny krok ma własny immutable manifest. Jedna pozycja opisuje
zamknięty rodzaj materiału, bezpieczną ścieżkę względną w kontrolowanym katalogu źródłowym,
liczbę bajtów oraz kryptograficzny hash tych bajtów. Ścieżka absolutna, `..`, symlink i plik
spoza kontrolowanego korzenia są odmową. Pusty manifest jest legalnym faktem „ten krok nie miał
plikowego wejścia”; brak manifestu dla nowego biegu nie znaczy pustego manifestu.

Manifest jest per **physical step UUID**, nie per nazwa kafelka ani logiczny step id: dwie kopie
i dwie rundy pętli mogą mieć inne wejścia. Powstaje z tego samego zamrożonego zbioru bajtów, z
którego Loadout buduje prompt i staging; nie jest raportem dopisywanym po starcie sterownika.
Stare receipts bez tego manifestu pozostają czytelne, ale nie mogą udawać dokładnego rerunu —
`again`/`onward` odmawiają takim biegom zdaniem mówiącym, że wejścia nie zostały zapisane.

## AC-1 Rerun wymaga całego zadeklarowanego wejścia fizycznego kroku
check: cargo test --test t154_rerun_replays_declared_step_inputs
expect: (\d+) passed

Produkcyjny bieg zapisuje dla dwóch fizycznych kroków różne manifesty zawierające handoffy i
powiązane attachments. `again` wybiera manifest dokładnego starego physical step UUID; `onward`
wybiera deklarowane wejście punktu wznowienia i nie zasiewa materiałów, których ten krok nie
otrzymał. Zdrowa scena odtwarza wszystkie bajty i startuje fake-driver dokładnie raz.

Osobne sceny po zakończeniu starego biegu usuwają zadeklarowany plik, zmieniają jego bajty przy
tej samej długości, podmieniają rozmiar, podstawiają symlink i odbierają odczyt kontrolowanego
katalogu. Każda odmawia przed driverem, nazywa bezpieczną względną ścieżkę i nie interpretuje
braku jako pustego katalogu. Nieuszkodzony plik leżący obok, lecz niewymieniony w manifeście,
nie jest wymagany ani kopiowany. Stary zdrowy kontrakt T-88 nadal przechodzi.

Uszkodzony `run.json` nie jest sceną tego AC: rerun potrzebuje go do znalezienia workflowu i
kroku niezależnie od kontekstu, więc jego odmowa nie dowodzi closure manifestu.

## AC-2 Staging, prompt i jawna capability mają dokładnie ten sam zbiór
check: cargo test --test t154_step_input_stage_matches_manifest
expect: (\d+) passed

Obok dozwolonych plików A i attachment A leżą sentinele B. Produkcyjna droga Start tworzy
prywatny katalog wejścia fizycznego kroku i publikuje w nim wyłącznie A, attachment A oraz
manifest opisujący dokładnie ich ścieżki, bajty i hashe. Fake-driver odbiera prawdziwy `RunSpec`:
prompt wskazuje wyłącznie ścieżki ze stagingu, a jawnie przekazane katalogi nie obejmują wspólnych
`handoffs/`, `attachments/` ani katalogu innego kroku. Driver znajduje A i nie znajduje B.

Fault przed publikacją stagingu zostawia zero widocznego stagingu; fault w commit point zostawia
albo poprzednią pełną wersję, albo pełną nową. Manifest nigdy nie wskazuje pliku, którego nie ma.
Po sukcesie test czyta staged bytes ponownie i sprawdza hash, zamiast ufać wartościom w pamięci.

Skills nie są zakresem tego zadania. Nie zamraża ono `SKILL.md`, nie dodaje skill hashy i nie
przenosi polityki materializacji skills; ten osobny lifecycle pozostaje poza T-154.
