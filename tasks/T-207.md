# T-207 — Receipt mówi prawdę o terminalności, wykonaniu i użyciu Codexa

Ostatnia diagnostyka pokazała trzy różne fakty zlane w jedno `complete`: terminalny
`startFailed`, niekompletne evidence i stary katalog bez `run.json`. Jednocześnie liczniki Codex
App Servera nie są filtrowane po aktywnym thread/turn i potrafią doliczyć replay albo spóźnioną
aktualizację poprzedniej tury. Ten task naprawia prawdę receipts i diagnostyki oraz przenosi
nullable fakt wykonania T-152 do istniejącego panelu historii. Nie sprząta historii, nie rozszerza
provenance i nie ustala budżetu startu — to robi T-208.

**Zależy od:** T-152, T-156 i T-201.

**Tryb:** direct medium, bez pełnego Harnessu. Osobny worktree, celowane czerwone testy,
`./verify.sh quick`, read-only diff review i pojedyncze `integrate.sh`.

## AC-1 Receipt i diagnostyka rozdzielają terminalność, kompletność i zastosowanie proofa
check: cargo test --test t207_receipt_and_diagnostics_tell_the_truth
expect: (\d+) passed

Produkcyjne drogi Run i `/ask` zapisują osobno terminalność logicznej próby, kompletność evidence,
fakt startu procesu oraz zastosowanie dowodu zejścia. `start -> Err` bez procesu jest terminalne,
ma `process_started: false` i nie wymaga fikcyjnego death proof. Started process nie może być
opisany jako zakończony bez `death_proof: true` albo typowanego `cleanup-needed`. Stare receipt bez
faktu startu procesu czytają się jako `unknown`, nigdy jako zmyślone `false`.

Diagnostyka nie zamienia brakującego albo uszkodzonego `run.json` ani `conversation.json` w pusty
normalny rekord. Zwraca typowany legacy/recovery problem z bezpieczną ścieżką. Task nie utrwala
`settled`, nie dokłada build SHA, wersji aplikacji, project base HEAD ani dirty fingerprintu: ten
kontrakt naprawia prawdę wykonania, nie rozszerza provenance.

## AC-2 Tokeny i koszt należą wyłącznie do aktywnej tury
check: cargo test --test t207_codex_usage_is_scoped
expect: (\d+) passed

Atrapa App Servera wysyła wiele `thread/tokenUsage/updated`: aktywny thread/turn, spóźnioną
aktualizację poprzedniej tury, replay, reset i kumulatywne `last`/`total`. Produkcyjny decoder
liczy wyłącznie monotoniczną deltę aktywnej tury i nie dodaje ponownie wartości kumulatywnej.
Receipt zachowuje rozdzielone input/output/cached. Nie wymusza `spent_usd` bez `budget_usd`;
istniejąca para limit/wydanie pozostaje uczciwa. Gdy semantyka eventu albo tabela cenowa nie jest
dowiedziona dla modelu lub tieru, `cost_usd` jest `null` z nazwanym powodem, nie zgadywaną kwotą.

## AC-3 Człowiek widzi, czy historyczny krok naprawdę ruszył
check: npx --no-install vitest run src/sections/run/past/t207-receipt-problems-are-visible.test.tsx
expect: (\d+) passed

Target przechodzi przez istniejące produkcyjne `listRuns`/`readRun` oraz `openHistoryFromLine`
i renderuje prawdziwy panel History. Nullable `executed` z T-152 dociera do frontendowego
`PastStep` bez zgadywania na podstawie statusu, czasu, PID albo artefaktów. Rozwinięty szczegół
kroku pokazuje dokładnie jedno z trzech zdań: `This step ran.`, `This step did not start.` albo
dla starego receiptu `This older run does not say whether this step ran.`. Target obejmuje
wszystkie trzy wartości i asertuje je w prawdziwym markupie panelu.

Zdrowy bieg nadal pokazuje kroki, handoffy i gałęzie. Ten AC nie tworzy drugiego panelu problemów
evidence, nie dubluje istniejącej obsługi brakującego `run.json` i nie obiecuje frontendowych
faktów, których wire historii nie niesie.
