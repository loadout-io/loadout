# T-153 — Równoległe prace składają się w osiągalne drzewo Git

Tekstowy fan-in działa: downstream dostaje raporty rodziców. Pliki nie składają się jednak wcale.
Dwa `fresh-copy` startują z tego samego stanu, a `same-copy` z kilkoma fizycznymi rodzicami jest
odmową. Workflow Backend + Frontend → Combine → Check może więc mieć prawdziwy overlap i poprawne
handoffy, a mimo to Combine widzi pliki tylko jednej albo żadnej gałęzi.

Nie powstaje nowy rodzaj kafelka ani ukryty etap schedulera. Jeden fizyczny poprzednik
`same-copy` zachowuje dzisiejsze zachowanie. Kilka kompatybilnych, Loadout-owned checkpointów Git
tworzy przy starcie downstream osobną kopię integracyjną, którą ten krok i jego późniejszy Check
kontynuują. Równoległe rodzeństwo nadal nigdy nie pisze do tej samej fizycznej kopii.

**Zależy od:** T-201; T-152 i T-202 są zależnościami tranzytywnymi.

## Kontrakt fizycznego fan-in

Przy planowaniu bieg tworzy jeden immutable Git seed dokładnych bajtów startowych projektu,
łącznie z ludzkim tracked i nieignorowanym untracked WIP. Każdy `fresh-copy` tego biegu odchodzi
od tego samego seedu, dzięki czemu ludzki WIP występuje w integracji raz, a nie raz na rodzica.
Loadout nie zmienia indeksu, working tree ani branchy głównego projektu.

Po zakończeniu procesu rodzica Loadout może utworzyć checkpoint dopiero, gdy T-201 zwrócił
`GroupProof::Dead` i wynik rodzica jest udany. Checkpoint jest immutable, osiągalnym refem,
którego tree opisuje dokładne końcowe tracked + nieignorowane untracked bajty rodzica względem
seedu. Działa także, gdy agent sam zrobił commit albo zostawił czysty worktree. Failed,
Cancelled i `cleanup_needed` nie są checkpointowane ani integrowane.

Wielorodzicowy `same-copy` jest legalny tylko wtedy, gdy każdy wybrany rodzic ma kompatybilny
Loadout-owned checkpoint z tego samego repo i seedu. Kopia integracyjna zaczyna od seedu i scala
delta w stabilnej kolejności planu grafu, nigdy w kolejności zakończenia procesów. Automatyczne
operacje Git nie uruchamiają hooków projektu, edytora ani podpisywania. Integracyjny ref i refy
rodziców pozostają osiągalne po biegu; wynik nie jest automatycznie mergowany do projektu.

## Uczciwe `before`

Wszystkie trzy dokładne Rustowe targety oraz kompilowalne typy checkpointu i fizycznej lineage
istnieją przed `./verify.sh before`. Targety używają prawdziwych repozytoriów Git, produkcyjnej
drogi Run, wykonywalnych fake-driverów i prawdziwego Check; nie testują osobnego algorytmu merge.
Padają na asercji brakujących bajtów, uruchomionego downstream mimo konfliktu albo pomieszanej
lineage. Brak symbolu, compile error, zero testów, timeout, sama liczba wywołań i frontendowy prop
nie są czerwienią.

## AC-1 Downstream i Check widzą dokładne bajty wszystkich rodziców
check: cargo test --test t153_git_fan_in_converges
expect: (\d+) passed

Prawdziwe repo zaczyna z ludzkim tracked i untracked WIP. Dwa równoległe `fresh-copy` mają
zmierzony overlap i tworzą rozłączny pełny przekrój zmian: nowe pliki tekstowe i binarne, zmianę
istniejącego pliku, rename, deletion, executable bit oraz symlink. Jeden rodzic sam tworzy commit
ze swojej pracy i kończy z czystym worktree, drugi zostawia tracked i untracked delta.

Po udanym, udowodnionym końcu obu rodziców `same-copy` tworzy kopię integracyjną. Downstream
fake-driver odczytuje wszystkie dokładne bajty i tryby; ludzki WIP występuje raz. Następnie
produkcyjny Check uruchomiony w **tej samej fizycznej kopii** weryfikuje identyczny tree i przechodzi.
Oracle nie poprzestaje na handoffach, nazwach branchy ani liczbie procesów.

Po normalnym zakończeniu worktree są posprzątane zgodnie z T-95, ale seed, checkpoint każdego
rodzica oraz finalny integracyjny ref są osiągalne przez `git rev-parse` i odtwarzają oczekiwane
tree. Główny projekt, jego indeks, WIP i aktualna gałąź pozostają bajtowo/refsowo baseline'em.
Także rodzic bez delta zostawia osiągalny checkpoint, jeśli jego udział jest potrzebny do
lineage; czysty wynik nie może zamienić rodzica w „brak".

Refy używają istniejącego namespace gałęzi danego runu. Produkcyjne `read_run` z History zwraca
checkpointy rodziców i finalny ref z nazwą właściwego kroku, a istniejąca akcja `Forget the
branches` potrafi je później zdjąć po tych samych guardach co dzisiejsze zachowane gałęzie.
Nie powstaje ukryty ref, którego nie pokazuje ani nie czyści żaden produkcyjny caller.

Scena z Failed, Cancelled i kontrolowanym `cleanup_needed` dowodzi, że żaden z tych rodziców nie
tworzy checkpointu ani nie trafia do integracji. Istniejąca polityka `whenItFails` nadal decyduje,
czy downstream w ogóle może być rozważony; fan-in nie tworzy drugiej polityki porażki.

## AC-2 Konflikt i nieobsługiwane źródło odmawiają bez zgadywania
check: cargo test --test t153_git_fan_in_refuses_conflicts
expect: (\d+) passed

Dwa udane checkpointy zmieniają tę samą linię różnie. Integracja w stabilnej kolejności wykrywa
konflikt, lecz nie wybiera pierwszego ani ostatniego rodzica. Downstream driver i Check mają zero
startów, żaden osiągalny ref nie zawiera markerów konfliktu, a oba checkpointy rodziców pozostają
osiągalne.

Produkcyjny kanał Run publikuje angielskie zdanie widoczne w feedzie, które nazywa bezpieczną
ścieżkę konfliktu i obu rodziców nazwami z kafelków. Nie pokazuje surowej komendy Git, SHA ani
żargonu worktree. Target odbiera zdarzenie tą samą drogą co okno; nie asertuje wyłącznie
`MergeError` z prywatnego helpera.

Osobne grafy wymagają wielorodzicowego fan-in w folderze bez Git, z rodzicem pracującym
bezpośrednio w `project` albo z planowanymi źródłami z niekompatybilnych repo/seedów.
`check_to_run` odmawia każdy z nich przed pierwszym procesem **całego biegu** i nazywa bezpieczny
powód. Nie istnieje fallback
kopiujący pliki, „last writer wins" ani drugi algorytm merge poza Git. Jednorodzicowy
`same-copy` i workflow bez fan-in nadal przechodzą dotychczasowy preflight.

## AC-3 Każda kopia pętli zachowuje własną fizyczną lineage
check: cargo test --test t153_copied_loop_preserves_physical_lineage
expect: (\d+) passed

Produkcyjny graf z `copies: 2` przechodzi dwie rundy z verifierem. Plan i runtime niosą stabilną
tożsamość fizycznej kopii oddzielną od logicznego klucza kafelka i numeru rundy. W rundzie drugiej
kopia 1 dostaje własny wynik i własną kopię plików z rundy pierwszej oraz wspólną decyzję
verifiera — nigdy wynik ani drzewo kopii 2. Kopia 2 zachowuje analogiczną lineage.

Po zakończeniu pętli synteza dostaje ostatni **rzeczywiście wykonany** wynik każdej kopii dokładnie
raz, z podpisami `(1 of 2)` i `(2 of 2)`. Jeśli jedna kopia została wcześniej settled i nie
wykonała kolejnej rundy, używany jest jej ostatni wykonany wynik, a nie pusty placeholder ani
wynik sąsiada. Handoffy i fizyczne foldery są wyszukiwane po physical copy identity, nie przez
„ostatni step o tej nazwie".

Target zapisuje rozróżnialny tekst i plik w każdej kopii każdej rundy, przechwytuje pełne prompty
i odczytuje finalne drzewa. Liczba wywołań, same nazwy `(1 of 2)` i logiczne step id nie są
wystarczającym oracle.
