# T-153 — Równoległe gałęzie składają się w jedno działające drzewo

Tekstowy fan-in działa, lecz zmiany plikowe nie. Dwa `fresh-copy` startują z tego samego HEAD,
a downstream dostaje raporty, nie ich pliki. To łamie faktyczne workflowy Backend + Frontend →
Combine → QA.

Nie dodajemy czwartego rodzaju kafelka ani ukrytego etapu w schedulerze. Rozszerzamy istniejące
`same-copy`: jeden fizyczny poprzednik zachowuje dzisiejsze zachowanie, a kilka różnych kopii
tworzy jawną kopię integracyjną przed startem downstream.

To wąsko zastępuje odmowę multi-parent `same-copy` z T-56. Nie osłabia T-95: równoległe rodzeństwo
nadal nie może pisać do tej samej fizycznej kopii. Fan-in dostaje nową kopię dopiero po trwałym
checkpointcie każdego udanego rodzica.

## Uczciwe `before`

Rustowe targety używają prawdziwego repo Git i produkcyjnej drogi Run; frontendowy montuje
prawdziwy panel. Szkielety kompilują się, a czerwień pochodzi z braku plików, pomieszanej
lineage lub niedostępnej kontrolki.

## AC-1 Downstream i Check widzą zmiany wszystkich rodziców
check: cargo test --test t153_parallel_file_work_converges
expect: (\d+) passed

Dwa równoległe kroki `fresh-copy` w realnym repo tworzą pełny przekrój zmian: nowe pliki
tekstowe i binarne, zmianę istniejącego pliku, rename, deletion i symlink. Po sukcesie każdego
rodzica, a przed zwolnieniem fan-in, Loadout tworzy immutable checkpoint jego dokładnego
tracked+untracked delta. Nie checkpointuje ani nie integruje rodzica Failed/Cancelled.

Kopia integracyjna powstaje dopiero przy starcie `same-copy` z kilkoma rodzicami. Scala ich
checkpointy w stabilnej kolejności, a potem ten krok i prawdziwy Check w tej samej kopii widzą
wszystkie dokładne bajty. Automatyczne operacje Git nie uruchamiają hooków projektu, edytora ani
podpisywania commitów i nie mutują głównego projektu. Branch integracyjny jest osiągalny po biegu,
także gdy checkpoint pozostawił czysty worktree; finalny rezultat nie jest automatycznie mergowany
do projektu.

Kontrola konfliktu zmienia tę samą linię różnie w obu kopiach. Downstream driver nie startuje,
widoczne zdanie nazywa ścieżkę i obu rodziców, a obie gałęzie/checkpointy pozostają osiągalne.
Żaden rodzic nie wygrywa przez kolejność, a driver nigdy nie widzi markerów konfliktu. Workflow
wymagający wielorodzicowego fan-in w folderze bez Gita jest odmową preflight przed pierwszym
procesem całego biegu; nie istnieje drugi, plikowy algorytm merge.

## AC-2 Każda kopia pętli zachowuje własną historię
check: cargo test --test t153_copied_loop_keeps_physical_lineage
expect: (\d+) passed

Krok `copies: 2` przechodzi dwie rundy z verifierem. Kopia 1 w następnej rundzie dostaje własny
poprzedni wynik i wspólną decyzję, nigdy wynik kopii 2; kopia 2 analogicznie. Synteza po pętli
dostaje ostatni rzeczywiście wykonany wynik obu kopii dokładnie raz, z prawdziwymi podpisami
`(1 of 2)` i `(2 of 2)`. Oracle nie poprzestaje na liczbie wywołań ani nazwach.

## AC-3 Agent potrafi wybrać ciągłość pracy z prawdziwej kontrolki
check: npx --no-install vitest run e2e/tests/t153-agent-can-continue-file-work.spec.ts
expect: (\d+) passed

Prawdziwy panel agenta pozwala wybrać `folder.use = same-copy`; zapis, zamknięcie i ponowne
otwarcie pokazują ten sam wybór. Angielska etykieta mówi o kontynuowaniu pracy w plikach,
nie o worktree/branchu. `project`, `fresh-copy` i `same-copy` są wzajemnie jednoznaczne.
Kontrolka nie obiecuje automatycznego lądowania zmian do projektu.
