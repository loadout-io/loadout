# T-153 — Równoległe prace składają się w osiągalne drzewo Git

Tekstowy fan-in działa: downstream dostaje raporty rodziców. Pliki nie składają się jednak wcale.
Dwa `fresh-copy` startują z tego samego stanu, a `same-copy` z kilkoma fizycznymi rodzicami jest
odmową. Workflow Backend + Frontend → Combine → Check może więc mieć prawdziwy overlap i poprawne
handoffy, a mimo to Combine widzi pliki tylko jednej albo żadnej gałęzi.

Nie powstaje nowy rodzaj kafelka ani ukryty etap schedulera. Jeden fizyczny poprzednik
`same-copy` zachowuje dzisiejsze zachowanie. Kilka kompatybilnych, Loadout-owned checkpointów Git
tworzy przy starcie downstream osobną kopię integracyjną, którą ten krok i jego późniejszy Check
kontynuują. Równoległe rodzeństwo nadal nigdy nie pisze do tej samej fizycznej kopii.

**Zależy od:** T-201; T-152 i stack T-202/T-210 są zależnościami tranzytywnymi.

- Harness prowadzi uczciwe czerwone `before`, quick/full, jedną recenzję i najwyżej jedną rundę

  zatrzymują pracę dla człowieka.
- Jedyne lądowanie to pojedyncze `integrate.sh` dla gałęzi zwróconej przez Harness. Nie zmieniaj
  `harness/`, `checks/` ani `verify.sh` i nie implementuj „merge przez prompt".
- Repozytoria testowe mają lokalną, fikcyjną tożsamość Git, aktywne hooki-sentinels i fikcyjny
  custom merge driver. Dowodzą, że produkcyjne operacje Loadout używają kontrolowanego pustego
  `hooksPath`, wyłączają signing/editor i odmawiają przed wykonaniem zewnętrznego merge drivera.
  Ciężkie Cargo biegnie pojedynczo na całej maszynie.

## Kontrakt fizycznego fan-in

Po czystym planowaniu i zielonym preflight, jako część transakcyjnego przygotowania z T-152,
bieg ustala jeden wspólny Git seed odpowiadający dokładnie dzisiejszej kopii `fresh-copy`:
`HEAD` plus tracked WIP człowieka. Nieignorowane untracked pliki człowieka zachowują istniejący
kontrakt `left_behind`; ten task nie dodaje ich po cichu do Git ani jego object database.
Przygotowanie nie zmienia HEAD, aktualnej gałęzi, indeksu, working tree ani istniejących refów
użytkownika, a jego własny stan wchodzi pod ten sam provisional guard co worktree. Exact-seed
materialization nakłada tracked WIP dokładnie raz, we wspólnej warstwie seedu. Nie wolno użyć
dzisiejszego `make_from(from)` w sposób, który po utworzeniu seedu ponownie zastosuje `diff HEAD`
w każdej kopii.

Przy zdrowym resume per-source tipy mogą być różne, ale produkcyjne planowanie dowodzi z historii
Git jednego wspólnego przodka-seedu, od którego wszystkie pochodzą. Może nim być użytkownikowy
`HEAD` albo commit seedu utworzony przez Loadout; autorytetem jest ancestry i exact OID, nie nazwa
refa. Poprzednie delty i
bieżący tracked WIP są składane nad jedną wspólną warstwą seedu, nigdy przez niezależne ponowne
nakładanie tego samego WIP per źródło. Brak jednego ancestry-proven seedu albo konflikt podczas
zbudowania tej warstwy jest odmową przed przygotowaniem; samo przypadkowe podobieństwo tree nie
jest dowodem wspólnej lineage.

Po udanym wyniku rodzica i `GroupProof::Dead` Loadout zapisuje jego końcowy tracked oraz
nieignorowany untracked stan jako commit checkpointu. Commit jest identyfikowany OID-em; nie
wymaga osobnego trwałego refu. Działa również, gdy agent sam zrobił commit, zakończył z czystym
worktree albo nie zmienił plików — wtedy checkpoint może wskazywać istniejący commit seedu.
Failed, Cancelled i `cleanup_needed` nie są źródłami fan-in. Błąd utworzenia checkpointu
przechodzi przez istniejący failure funnel rodzica, zamiast publikować sukces bez plików.

Wielorodzicowy `same-copy` tworzy kopię integracyjną dopiero, gdy staje się runnable. Zaczyna od
wspólnego seedu i scala udane checkpointy w stabilnej kolejności grafu, nigdy w kolejności
zakończenia procesów. `carry-on` może przekazać tekstowy powód Failed/Cancelled rodzica, ale nigdy
jego pliki; przy jednym udanym fizycznym źródle downstream kontynuuje je bez merge, a przy zerze
źródeł odmawia. Po sukcesie finalny integracyjny ref osiąga commity rodziców; osobne refy seedu i
rodziców nie muszą zostać. Po konflikcie finalny ref i tymczasowa kopia integracyjna nie zostają,
a gałęzie rodziców pozostają osiągalne. Wszystkie automatyczne operacje idą przez jeden
kontrolowany runner Git: używają pustego katalogu `hooksPath` należącego do biegu, wyłączonego
signingu i nieinteraktywnego editora oraz środowiska oczyszczonego z odziedziczonych `GIT_*`
poza jawną allowlistą potrzebną tej operacji. Jeśli dla scalanej ścieżki Git wybrałby custom
merge driver, Loadout odmawia przed jego wykonaniem; nie uruchamia projektu i nie zastępuje go
drugim algorytmem. Dozwolone nowe obiekty, administracja worktree i refy powstają wyłącznie w
namespace Loadouta; istniejące refy użytkownika pozostają nietknięte. Wynik nie jest automatycznie
mergowany do projektu.

## Uczciwe `before`

Wszystkie trzy dokładne Rustowe targety oraz każdy importowany przez nie nowy moduł lub symbol
istnieją przed `./verify.sh before`. Targety używają prawdziwych repozytoriów Git, produkcyjnej
drogi Run, wykonywalnych fake-driverów i prawdziwego Check; nie narzucają prywatnej nazwy typu ani
nie testują osobnego algorytmu merge. Każdy target ma osiągalną przed implementacją asercję
właściwego zachowania. Dzisiejsza ogólna odmowa multi-parent `same-copy` nie jest właściwym oracle
dla brakujących bajtów, konfliktu ani lineage: target musi odróżnić ją od oczekiwanego sukcesu lub
odmowy dopiero po wykonaniu rodziców. Brak symbolu, compile error, zero testów, timeout i sama
liczba wywołań nie są czerwienią.

## AC-1 Downstream i Check widzą dokładne bajty wszystkich rodziców
check: cargo test --test t153_git_fan_in_converges
expect: (\d+) passed

Prawdziwe repo zaczyna z tracked WIP człowieka oraz osobnym nieignorowanym untracked sentinelem.
Dwa równoległe `fresh-copy` mają zmierzony overlap i tworzą rozłączny przekrój zmian: nowe pliki
tekstowe i binarne, zmianę istniejącego pliku, rename, deletion, executable bit oraz symlink.
Jeden rodzic sam tworzy commit i kończy z czystym worktree, drugi zostawia tracked i untracked
delta. Obie kopie startują z identycznego seedu; tracked WIP występuje w wyniku raz, a ludzki
untracked sentinel pozostaje wyłącznie w projekcie i w istniejącym `left_behind`.

Pierwsza asercja targetu przechwytuje wynik produkcyjnego Run i wymaga, żeby plan został przyjęty,
obaj rodzice naprawdę wystartowali oraz mieli zmierzony overlap. Na kodzie `before` pada więc na
asercji oczekiwanego przyjęcia zamiast zaliczyć dzisiejszą generyczną odmowę jako zastępstwo
brakujących bajtów. Dopiero po tej granicy oracle czyta wynik fan-in.

Po udanym, udowodnionym końcu obu rodziców `same-copy` tworzy kopię integracyjną. Downstream
fake-driver odczytuje wszystkie dokładne bajty i tryby, a produkcyjny Check w tej samej fizycznej
kopii weryfikuje identyczny tree. Oracle nie poprzestaje na handoffach, nazwach branchy ani liczbie
procesów. Fixture instaluje hooki oraz ustawia odziedziczone edytory i merge-autoedit na programy
zapisujące zewnętrzny sentinel; żaden hook ani editor nie rusza.

Po zakończeniu worktree są posprzątane zgodnie z T-95. Finalny integracyjny ref jest osiągalny,
odtwarza oczekiwany tree i ma checkpointy rodziców jako przodków; nie zostają obowiązkowe puste
refy seedu ani rodzica bez delta. Istniejące History i `Forget the branches` widzą oraz zdejmują
finalny ref przez obecny namespace biegu, bez nowego kształtu History. Projekt, jego indeks, WIP,
HEAD, aktualna gałąź i istniejące refy pozostają baseline'em.

Parametryzowana kontrola Failed, Cancelled i `cleanup_needed` dowodzi, że żaden taki rodzic nie
trafia do integracji. Jego odzyskiwalna praca zachowuje dotychczasowy kontrakt T-95/T-201, a
`whenItFails` nadal samodzielnie decyduje, czy downstream może być rozważony.

## AC-2 Konflikt i nieobsługiwane źródło odmawiają bez zgadywania
check: cargo test --test t153_git_fan_in_refuses_conflicts
expect: (\d+) passed

Dwa udane checkpointy zmieniają tę samą linię różnie. Integracja w stabilnej kolejności wykrywa
konflikt, lecz nie wybiera pierwszego ani ostatniego rodzica. Downstream driver i Check mają zero
startów, finalny integracyjny ref i tymczasowy worktree nie zostają, żaden osiągalny commit nie
zawiera markerów konfliktu, a gałęzie obu rodziców pozostają osiągalne.

Produkcyjny kanał Run publikuje angielskie zdanie widoczne w feedzie, które nazywa bezpieczną
ścieżkę konfliktu i obu rodziców nazwami z kafelków. Nie pokazuje surowej komendy Git, SHA ani
żargonu worktree. Target odbiera zdarzenie tą samą drogą co okno; nie asertuje wyłącznie
`MergeError` z prywatnego helpera. Przed asercją odmowy target dowodzi, że obaj rodzice naprawdę
wystartowali, zakończyli się z `GroupProof::Dead` i opublikowali checkpointy. Dzisiejsza odmowa
podczas planowania nie spełnia tej sceny i nie jest jej uczciwą czerwienią.

`check_to_run` pozostaje statycznym walidatorem grafu i deklarowanych folderów: odmawia
wielorodzicowemu `same-copy`, gdy co najmniej jedno fizyczne źródło jest `project`/`pick`, bez
zgadywania czegokolwiek o wybranym workspace. Fakty zależne od uruchamianego folderu należą do
produkcyjnego, read-only preflightu `plan_run`: przed katalogiem biegu, przygotowaniem i driverem
odmawia on fan-inowi bez Git oraz resume bez jednego ancestry-proven seedu. Target dochodzi tam
produkcyjną drogą Run/resume, nie przez ręcznie złożony prywatny typ, i asertuje właściwy typ oraz
konkretny powód odmowy; sama wcześniejsza generyczna odmowa multi-parent nie wystarcza. Nie istnieje
fallback kopiujący pliki, „last writer wins" ani drugi algorytm merge poza Git. Jedno fizyczne
źródło — także kilka logicznych krawędzi deduplikujących się do niego — oraz workflow bez fan-in
zachowują dotychczasowe zachowanie.

Osobna scena przypisuje konfliktowej ścieżce przez `.gitattributes` fikcyjny custom merge driver,
którego program zapisałby sentinel poza repo. Produkcyjna droga rozpoznaje wybrany driver i odmawia
przed jego wykonaniem: sentinel nie powstaje, rodzice pozostają osiągalni, a downstream ma zero
startów. Sam wpis `merge.<name>.driver` w konfiguracji bez przypisania go do scalanej ścieżki nie
jest odmową.

## AC-3 Każda kopia pętli zachowuje własną fizyczną lineage
check: cargo test --test t153_copied_loop_preserves_physical_lineage
expect: (\d+) passed

Produkcyjny graf z `copies: 2` wykonuje kontrolę z przejściem po pierwszej rundzie oraz kontrolę
z przejściem po drugiej. Plan i runtime zachowują fizyczną tożsamość kopii niezależnie od klucza
kafelka i rundy. W rundzie drugiej kopia 1 dostaje własny wcześniejszy wynik i własne bajty z
rundy pierwszej oraz wspólną decyzję verifiera — nigdy wynik ani drzewo kopii 2; kopia 2
analogicznie.

Po wyjściu z pętli synteza dostaje ostatni rzeczywiście wykonany wynik obu kopii dokładnie raz,
z podpisami `(1 of 2)` i `(2 of 2)`. Przy przejściu w pierwszej rundzie dostaje oba wyniki rundy
pierwszej; przy przejściu w drugiej — oba wyniki rundy drugiej. Nie dostaje niewykonanego
placeholdera ani wyniku sąsiada. Lookup handoffu i folderu używa fizycznej tożsamości kopii,
nie pierwszego lub ostatniego kroku o tej samej nazwie.

Target zapisuje rozróżnialny tekst i plik w każdej kopii każdej wykonanej rundy, przechwytuje
pełne prompty oraz bajty widziane przez sterowniki i finalny fan-in. Liczba wywołań, same podpisy
kopii i logiczne step id nie są wystarczającym oracle. Dla uczciwego `before` target najpierw
wykonuje osiągalną scenę lineage, w której każda kopia kończy rundę pojedynczym fizycznym
następcą, i asertuje własny wcześniejszy tekst oraz plik przed dołożeniem finalnej syntezy. Dzięki
temu czerwień pochodzi z pomieszanej fizycznej kopii, a nie z dzisiejszej ogólnej odmowy fan-in;
po naprawie ten sam target dowodzi także końcowej syntezy wielorodzicowej.
