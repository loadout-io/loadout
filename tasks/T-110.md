# T-110 — Lead na Codeksie startuje, wyjaśnia odmowę i nie uruchamia prywatnych MCP

To jest zastępstwo dla zamkniętego T-105. Dwa pierwsze defekty T-105 są nadal aktualne,
ale jego AC-3 wymagało `--ignore-user-config`, którego `codex app-server` nie przyjmuje.
Sonda wykonana przez kontrakt na `codex-cli 0.149.1` odrzuciła flagę przed i po
`app-server`. Sprawdzona następnie nakładka `-c 'mcp_servers={}'` też nie jest rozwiązaniem:
pusta tabela scala się niedestrukcyjnie i zostawia istniejące serwery włączone.

Cel D-4 nie zmienia się: prywatne serwery MCP z konfiguracji użytkownika nie mogą wejść
do leada. Po `initialize`, ale przed `thread/start`, sterownik czyta efektywną konfigurację
przez `config/read`. Każdy znaleziony identyfikator `mcp_servers` dostaje w polu `config`
żądania `thread/start` osobną nakładkę `mcp_servers.<id>.enabled=false`. To zachowuje
uwierzytelnienie z katalogu użytkownika i korzysta z publicznego szwu konfiguracji per wątek,
ale wyłącza właśnie boczną furtkę zmierzoną dla notion, figma i linear-server. Połączenia
produktu pozostają drogą do narzędzi leada.

## Kto to robi

- **Agent:** `rust-core`. Bez `run.rs`; musi wylądować przed T-102, bo oba dotykają
  `codex.rs`.
- **Druga opinia:** inny vendor niż pisarz (D3).

## AC-1 Słowa piaskownicy App Servera są tymi, które protokół przyjmuje
check: cargo test --test it codex_lead_sandbox_protocol::
expect: (\d+) passed

`app_server_sandbox` oddaje `read-only` / `workspace-write` / `danger-full-access` —
te same trzy napisy, które droga `exec` przekazuje przez `-s`. Fikstura prawdziwej drogi
leada przechwytuje żądanie `thread/start` i dowodzi kebab-case; kontrola wiąże oba miejsca
jedną tabelą, żeby nie rozjechały się ponownie.

## AC-2 Człowiek widzi kod i treść odmowy App Servera
check: cargo test --test it codex_lead_refusal_visible::
expect: (\d+) passed

Odpowiedź JSON-RPC z `error` daje zdanie odmowy z pełnym dynamicznym `error.code` oraz
`error.message` vendora. Kryterium idzie prawdziwą drogą sterownika do zdarzenia, które
dostaje okno — nie kończy na funkcji zwracającej wartość. Konkretna wiadomość fikstury
jest widoczna w tym zdarzeniu; odpowiedź bez `error` pozostaje kontrolą sukcesu.

## AC-3 Prywatne MCP użytkownika nie startują w leadzie
check: cargo test --test it codex_lead_private_mcp_disabled::
expect: (\d+) passed

Po `initialize`, lecz przed `thread/start`, produkcyjna droga pyta App Server o `config/read`.
Dla każdego klucza z efektywnego `config.mcp_servers` żądanie `thread/start` niesie osobny
wpis `config` ustawiający `<ten-id>.enabled=false`. Segment identyfikatora jest kodowany jako
bezpieczny segment klucza TOML; fikstura obejmuje zwykłą nazwę i nazwę z kropką/cudzysłowem,
żeby wpis użytkownika nie mógł zmienić ścieżki nakładki.

Fikstura App Servera odmawia `thread/start`, jeśli choć jeden zwrócony wcześniej serwer nie
jest wyłączony, i zostawia znacznik symulowanego startu prywatnego MCP. Właściwa droga kończy
handshake bez znacznika; kontrola bez nakładek zostawia znacznik. `config/read` z błędnym
kształtem lub błędem JSON-RPC odmawia startu leada ze zdaniem widocznym dla człowieka — nie
wraca po cichu do prywatnych narzędzi. Argv pozostaje co do bajta jak dziś. Test nie szuka
stringa w źródle i nie zapisuje konfiguracji użytkownika.
