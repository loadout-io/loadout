# T-163 — Domyślny Lead mieszka w Settings i zostaje z rozmową

Wybór Lead jest dziś ulotnym singletonem `src/sections/run/lead.ts`, stoi w pasku Run i jedzie
przez IPC przy **każdej** wiadomości. Rust za każdym razem ponownie otwiera bibliotekę Agentów,
zanim zapyta rejestr rozmów. Zmiana selecta nie potrafi więc przestawić żywej sesji, ale usunięcie
albo zepsucie wybranego pliku potrafi odmówić kolejnej tury sesji, która już działa. Kontrolka
obiecuje jedno, a runtime robi drugie.

To zadanie przenosi jeden globalny wybór do Settings, zapisuje wyłącznie identyfikator Agenta i
przypina rozwiązaną definicję do nowej rozmowy. Settings jest modalnym sheetem otwieranym kołem
zębatym w bocznym menu — nie siódmą sekcją i nie ustawieniem workspace'a. Vendor, model, wysiłek,
dostęp do plików, instrukcje i Connections nadal mają dokładnie jedną prawdę: plik Agenta
(`DECISIONS-LOCKED.md` D3 i D6).

Zadanie zamyka też zmierzony incydent z 2026-08-28. Projekt Meetnotes ma nazwany profil
`[permissions.murmur_harness_reviewer.*]`, lecz nie wskazuje rootowego `default_permissions`.
Codex App Server rozstrzyga konfigurację już podczas `config/read`, **przed** naszym jawnym
`thread/start.sandbox`, i odrzuca rozmowę kodem `-32603`. Zwykłe kroki nie pokazują wady, bo droga
`codex exec` używa `--ignore-user-config`; droga Lead przez App Server nie ma takiej flagi.
Sonda bez modelu na lokalnym `codex-cli 0.150.1` potwierdziła oba końce: bez override
`config/read` zwraca dokładnie `-32603`, a
`codex -c 'default_permissions=":danger-full-access"' app-server` przechodzi
`initialize`/`config/read` w Meetnotes i raportuje wybór z warstwy `sessionFlags`. Dostępne
built-iny tej wersji to `:read-only`, `:workspace` i `:danger-full-access`.
Naprawą nie jest edycja cudzego `.codex/config.toml` ani wybór przypadkowego profilu projektu.
Loadout podaje App Serverowi własny profil wbudowany, wyliczony z tego samego `Agent.fileAccess`,
który już ustala `thread/start.sandbox`. Dial Agenta pozostaje jedyną drogą polityki (§6b).

Zadanie nie zmienia workflowów, ich zakresu, pamięci/Learnings, układu paska kroków ani modelu
NOW. Nie importuje całego native profilu Codeksa: taki profil może zarówno zabraniać, jak i
rozszerzać dostęp. Ewentualna kuracja samych reguł deny wymaga osobnego, jawnego kontraktu.

**Zależy od:** T-158 i T-208. T-208 domyka wcześniejsze zmiany IPC/Run oraz tranzytywnie prywatny
transport T-205; T-158 kończy współdzielony `lib.rs`. Dzięki temu Settings nie ma drugiego writera
równolegle z fazą produkcyjnego domknięcia.

**Read first:** `AGENTS.md` niezmienniki 4, 9, 13, 16, 19, 23, 24 i 29 ·
`docs/DECISIONS-LOCKED.md` D3, D5 i D6 · `docs/ARCHITECTURE.md` §6b, §7 i §8 ·

`tasks/T-202.md`, `tasks/T-203.md`, `tasks/T-205.md` i `tasks/T-208.md` ·

## Tryb wykonania

- Codex w osobnym worktree po integracji T-158 i T-208, bez osobnego Harnessu.
- Uczciwe czerwone `before`, quick/full i read-only review; najwyżej jedna runda naprawy.
- Nie zmieniaj `harness/`, `checks/`, `verify.sh`, `docs/DECISIONS-LOCKED.md` ani plików T-161/T-162.
- Nie uruchamiaj dwóch ciężkich komend Cargo równolegle.

## Uczciwe `before`

Wszystkie cztery targety oraz każdy nowy importowany moduł istnieją przed
`./verify.sh before`. Rustowe API ma kompilowalny szkielet, frontendowy Settings może renderować
pusty sheet, a testy padają na asercji: braku trwałych bajtów, koła zębatego, przypięcia albo
argumentu App Servera. Brak modułu, błąd kompilacji, brak przeglądarki/fake vendora, zero testów
i sztuczny sentinel nie są czerwienią.

## AC-1 Globalne Settings zapisuje wyłącznie stabilny identyfikator
check: cargo test --test t163_default_lead_settings_are_durable
expect: (\d+) passed

Produkcyjny store czyta i zapisuje `<loadout-home>/settings.json` w schemacie:

```json
{
  "schemaVersion": 1,
  "defaultLeadAgentId": "01a015ac-0573-7a52-8569-3702dceca4b9"
}
```

`defaultLeadAgentId` jest `UUID | null`; w pliku nie ma nazwy, vendora, modelu, wysiłku,
file access, promptu ani Connections. Brak pliku oznacza `null` i nigdy nie wybiera pierwszego
Agenta z katalogu. Zapis niepustego ID przechodzi wyłącznie wtedy, gdy dokładnie ten zdrowy Agent
istnieje w globalnej bibliotece; problem definicji z T-203 nie staje się zmyślonym wyborem.

Publikacja używa wspólnego durable replace z T-202: temp w katalogu celu, pełny zapis, `sync_all`,
atomowa podmiana i synchronizacja katalogu. Fault-injection przed i w commit point zostawia stare
albo pełne nowe bajty, nigdy pusty/pół pliku. Plik z niepoprawnym JSON-em, złą wersją albo ID o
złym kształcie daje typowany, wykonalny błąd i nie jest automatycznie nadpisywany. Ponowne
otwarcie nowego store'a czyta ten sam wybór; SQLite i `ui.json` nie są drugim źródłem prawdy.

## AC-2 Koło zębate otwiera prawdziwe Settings, a Run nie wybiera Lead
check: npx --no-install vitest run e2e/tests/t163-settings-own-the-default-lead.spec.ts
expect: (\d+) passed

Spec uruchamia prawdziwą powłokę przez `e2e/harness.ts`. Dostępny przycisk z ikoną koła i
`aria-label="Settings"` stoi w stopce bocznego menu. Klik otwiera jeden sheet z
`role="dialog"`, `aria-modal="true"`, nagłówkiem `Settings`, przyciskiem `Close` i polem
`Default lead agent`. Sheet nie pojawia się w `SECTIONS`, nie zmienia aktywnej sekcji ani
workspace'a, zamyka się przez `Close` i Escape, a fokus wraca na gear.

Lista bierze zdrowych Agentów z istniejącej biblioteki. Po wyborze pokazuje tylko rozwiązane,
read-only podsumowanie tej samej definicji — nazwę, aplikację, model, thinking i file access —
oraz zdanie `Used for new conversations. Existing conversations keep their current lead.`
Zapis wysyła dokładnie UUID wybranego Agenta przez prawdziwą komendę Rusta; po ponownym
zamontowaniu ekranu, przełączeniu workspace'a i otwarciu sheeta widać odpowiedź od store'a,
nie lokalną kopię.

Ten sam prawdziwy ekran Run nie ma żadnego selecta `Lead agent`, nie pobiera listy Agentów dla
paska i nie importuje singletona wyboru. `src/sections/run/lead.ts` znika w całości. Wysłanie
wiadomości nie niesie pola `lead`; `say_to_orchestrator` dostaje tylko terminal, folder, tekst i
obrazy. Istniejące kontrolki workflowu, limitów i Stop pozostają działające.

Przypadki braku ustawienia i skasowanego Agenta wykonują prawdziwą drogę wpisu w Run. Pod wierszem
człowiek widzi odpowiednio `Choose a default lead agent in Settings.` albo
`Your default lead agent is no longer available. Choose another one in Settings.` Ani pusty
default, ani dangling UUID nie startuje procesu. Sheet pokazuje ten sam problem przy polu i nadal
pozwala wybrać zdrowego Agenta. Test nie montuje samego selecta i nie asertuje wyłącznie wartości
zwróconej przez helper (niezmiennik 29).

## AC-3 Jedna rozmowa zachowuje jednego rozwiązanego Agenta
check: cargo test --test t163_default_lead_is_pinned_per_conversation
expect: (\d+) passed

Target przechodzi przez produkcyjne `say_to_orchestrator_from_window`, rejestr `Threads` i fake
obu driverów. `open_chat` nadal tylko zakłada kanał: nie czyta Settings, nie wybiera Agenta i nie
startuje płatnej sesji. Pierwsza niepusta wiadomość nowej rozmowy atomowo:

1. czyta `defaultLeadAgentId` z globalnych Settings;
2. rozwiązuje dokładnie ten plik Agenta;
3. zamraża jego vendor, model, thinking, file access, instrukcje i Connections;
4. konfiguruje driver i dopiero po udanym starcie przypina snapshot do terminalu.

Po starcie ustawienie zmienia się z Agenta A na B, a plik A zostaje osobno zmieniony, usunięty i
zastąpiony wadliwym plikiem. Kolejne tury istniejącej rozmowy nadal trafiają do jednego uchwytu A
bez ponownego czytania Settings/biblioteki i bez drugiego procesu. Nowy terminal bierze B. Po
jawnym Close świeża rozmowa dawnego terminalu także bierze aktualny default. Dwie równoległe
pierwsze wiadomości nie tworzą dwóch sesji ani dwóch różnych pinów.

Brak Settings, `null`, dangling UUID i wadliwy plik Agenta odmawiają **przed** fabryką drivera,
każdy zdaniem kierującym do Settings. Nie ma fallbacku do pierwszego Agenta, Claude'a, ostatniego
wyboru w oknie ani domyślnego vendora. Komenda IPC nie przyjmuje już `lead`, więc stare albo
złośliwe okno nie potrafi ominąć globalnego ustawienia. Manifest/evidence pierwszej tury opisuje
ten sam przypięty Agent, którym naprawdę wystartował proces.

## AC-4 App Server dostaje jawny profil zgodny z `Agent.fileAccess`
check: cargo test --test t163_codex_app_server_has_owned_permissions
expect: (\d+) passed

Target uruchamia produkcyjny `CodexDriver::start_conversation` przeciw fake App Serverowi, który
odtwarza incydent: jego projektowa konfiguracja ma `[permissions.murmur_harness_reviewer.*]` bez
rootowego `default_permissions`, a `config/read` odrzuca żądanie kodem `-32603`, jeśli proces nie
dostał jawnej selekcji. Dla każdego file access argv zawiera dokładnie jedną globalną parę `-c`
przed `app-server`, a `thread/start.sandbox` niesie odpowiadający jej ten sam dial:

| `Agent.fileAccess` | `default_permissions` | `thread/start.sandbox` |
|---|---|---|
| `look-only` | `":read-only"` | `read-only` |
| `ask-first` | `":workspace"` | `workspace-write` |
| `work-freely` | `":danger-full-access"` | `danger-full-access` |

Mapowanie `FileAccess → Policy` pozostaje istniejącą jedną tabelą; adapter Codex tłumaczy tylko
`Policy → built-in profile/sandbox`. Jawny override należy do Loadouta, więc stoi w jednym
builderze App Servera, nie w Settings, pliku Agenta ani projekcie. `config/read`, kuracja MCP i
pierwsza tura dochodzą do końca; bajty `.codex/config.toml` są identyczne przed i po. Nie powstaje
prywatny `CODEX_HOME`, kopia auth ani zapis nazwy profilu projektu do argv/evidence.

`default_permissions`, rodzina `permissions.` i alternatywne spellingi, którymi da się wybrać
profil, dołączają do wspólnej polityki reserved Codex. Agent ani krok nie może ich przemycić w
`vendorOptions`; preflight odmawia, nazywając wiersz do usunięcia. Kontrola dodatnia dowodzi, że
zwykłe bezpieczne opcje vendora i zatwierdzone Connections nadal dojeżdżają. Nieznany błąd
`config/read` nadal fail-closed — jawny built-in naprawia tylko precedencję polityki, nie maskuje
uszkodzonego model catalog, auth ani dowolnego `-32603`.
